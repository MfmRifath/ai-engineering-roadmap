# L6 — Building Autonomous Assistants

> **Thesis:** Autonomy is a dial, not a switch — and the engineering work is deciding where the
> model decides and where your code decides.

## Why this chapter matters

It is the practical follow-on to [L1](ch01.md)'s autonomy levels: how do you actually *construct*
a system that is autonomous in the right places? Lanham's answer, which is the durable content, is
**hybrid control flow** — deterministic scaffolding with model decision points inserted where
dynamism is genuinely needed.

## Core concepts

### Where should the model decide?

The design question for every step in your system:

| Give it to the model when | Give it to code when |
|---|---|
| The path depends on content you cannot enumerate | The path is knowable in advance |
| Judgment or interpretation is required | A rule suffices |
| The input space is genuinely open | The input space is bounded |
| Being occasionally wrong is acceptable | Correctness is required |

**Every model decision point is a place your system can go wrong.** Minimize them, and put
verification around the ones you keep. A system with two model decisions inside a deterministic
scaffold is far more reliable than one with ten, and usually solves the same problem.

### Behaviour trees and structured control

Lanham brings in **behaviour trees** from game AI, which is a genuinely useful import. The
composition primitives:

- **Sequence** — run children in order; fail if any fails.
- **Selector / fallback** — try children in order until one succeeds. This is your retry and
  degradation logic.
- **Parallel** — run concurrently.
- **Decorator** — modify a child (retry *n* times, timeout, invert).
- **Condition / action** — leaves.

Why this matters beyond the specific formalism: it gives you **explicit, inspectable control
flow** with the model as a leaf node rather than as the orchestrator. You can reason about what
the system will do, because most of it is code.

That is the shape most reliable production "agents" actually take, and it is worth being explicit
that this is a *good* outcome rather than a failure to achieve full autonomy.

### The assistant loop, with guards

Building on [L1](ch01.md), a production loop needs:

- **Step cap** — always.
- **Cost budget** — always.
- **Wall-clock timeout** — the model can stall.
- **Loop detection** — the same tool with the same arguments twice is a signal, not a coincidence.
- **Progress checking** — is the agent actually advancing, or restating?
- **Graceful degradation** — a partial answer with an explanation beats an exception.

**Loop detection** deserves emphasis because it is the classic agent failure and it is cheap to
catch: hash (tool name, arguments) and count repeats. Two identical calls means the agent did not
learn from the first result, so feed that back explicitly — *"You already called this and got X;
try something else"* — rather than letting it spin.

### State management

An assistant needs to track: the goal, progress so far, what has been tried, what failed, and
intermediate results.

The naive approach — keep everything in the message history — hits the context limit and makes
each step more expensive ([L2](ch02.md)). The alternatives are the memory strategies from
[A7](../../02-hands-on-llms-alammar/notes/ch07.md) and [L8](ch08.md): windowing, summarization,
and external storage with retrieval.

A pattern worth knowing: keep a **compact structured scratchpad** — goal, findings, attempted
approaches, current step — updated by the agent and injected fresh each turn, rather than relying
on the raw conversation to carry state. It is cheaper, more reliable, and inspectable.

### Human in the loop

Three placements, and the choice per action matters:

| Pattern | When | Cost |
|---|---|---|
| **Approve before acting** | Irreversible or outward-facing actions | Latency, user attention |
| **Review after acting** | Reversible actions | Cleanup if wrong |
| **Escalate on uncertainty** | Low confidence or repeated failure | Requires a confidence signal |

The third is the most sophisticated and the least used. You need a confidence signal —
**logprobs** ([H2](../../04-ai-engineering-huyen/notes/ch02.md)), repeated tool failures, or an
explicit self-assessment — and a threshold for handing off. Building it means your agent fails
*loudly and usefully* instead of confidently.

## Key code

```python
# Loop detection: the classic agent failure, and cheap to catch
from collections import Counter
import json

class LoopGuard:
    def __init__(self, threshold: int = 2):
        self.seen, self.threshold = Counter(), threshold

    def check(self, call) -> str | None:
        key = (call.name, json.dumps(call.arguments, sort_keys=True))
        self.seen[key] += 1
        if self.seen[key] >= self.threshold:
            # Tell the agent what it did, don't just abort
            return (f"You have already called {call.name} with these exact arguments "
                    f"and received a result. Repeating it will not help — try a "
                    f"different tool or different arguments.")
        return None
```

```python
# A compact structured scratchpad beats relying on raw history to carry state
class Scratchpad(BaseModel):
    goal: str
    findings: list[str] = []
    attempted: list[str] = []
    blocked_by: str | None = None

    def render(self) -> str:
        return (f"GOAL: {self.goal}\n"
                f"FOUND: {'; '.join(self.findings) or 'nothing yet'}\n"
                f"TRIED: {'; '.join(self.attempted) or 'nothing yet'}\n"
                f"BLOCKED: {self.blocked_by or 'no'}")
```

```python
# The guarded loop: every bound is deliberate
def run_assistant(task, tools, *, max_steps=12, max_cost=1.0, timeout_s=120):
    guard, pad = LoopGuard(), Scratchpad(goal=task)
    start, cost = time.monotonic(), 0.0

    for step in range(max_steps):
        if time.monotonic() - start > timeout_s:
            return partial_result(pad, "timed out")
        if cost > max_cost:
            return partial_result(pad, "budget exceeded")

        resp = model(build_messages(pad), tools=tools, temperature=0)
        cost += resp.cost
        if not resp.tool_calls:
            return {"answer": resp.content, "steps": step, "cost": cost}

        for call in resp.tool_calls:
            if (warning := guard.check(call)):
                observe(warning)
                continue
            pad.attempted.append(call.name)
            observe(dispatch(call))

    return partial_result(pad, "step limit reached")   # degrade, don't raise
```

## Gotchas

- **Model decisions where a rule would do.** Every one is a failure point.
- **No loop detection.** The classic runaway.
- **Aborting on a detected loop instead of informing the agent.** Tell it what it repeated; it can
  often recover.
- **Relying on raw message history for state.** Expensive and unreliable; use a scratchpad.
- **No timeout.** Step caps do not protect against a slow provider.
- **Raising instead of degrading.** A partial answer with an explanation is more useful than a
  stack trace.
- **Human approval on everything.** Users stop reading and click through. Reserve it for genuinely
  consequential actions.
- **No confidence signal.** Without one, the agent cannot escalate and will fail silently.

## Exercises

**Understand**
1. When should a decision go to the model rather than to code?
2. Why is a behaviour tree with the model as a leaf more reliable than a model orchestrator?
3. Why inform the agent about a detected loop rather than aborting?
4. What signals can drive an escalation-on-uncertainty pattern?

**Build**
1. Add loop detection, a cost budget, a wall-clock timeout, and graceful degradation to your

4. Take a task currently done by an open loop and restructure it as a behaviour tree with two
   model leaves. Compare reliability and cost.

## Flashcards

<!-- card -->
Q: When should a decision be made by the model rather than by code?
A: When the path depends on content you cannot enumerate, judgment is required, the input space is genuinely open, and being occasionally wrong is acceptable. Otherwise a rule is more reliable and cheaper — and every model decision point is a place the system can go wrong.
<!-- /card -->

<!-- card -->
Q: What is loop detection and how should you handle a detected loop?
A: Hash (tool name, arguments) and count repeats; two identical calls means the agent did not learn from the first result. Handle it by telling the agent explicitly — "you already called this and got X, try something else" — rather than aborting, because it can often recover.
<!-- /card -->

<!-- card -->
Q: Why use a structured scratchpad instead of relying on message history?
A: Raw history grows every step, costs more each turn, and eventually exhausts the context. A compact scratchpad (goal, findings, attempted, blocked) is cheaper, more reliable, and inspectable.
<!-- /card -->

<!-- card -->
Q: What guards does a production agent loop need?
A: Step cap, cost budget, wall-clock timeout, loop detection, progress checking, and graceful degradation — returning a partial answer with an explanation rather than raising.
<!-- /card -->

<!-- card -->
Q: What is escalation-on-uncertainty and what does it require?
A: Handing off to a human when the agent is likely to be wrong. It requires a confidence signal — logprobs, repeated tool failures, or explicit self-assessment — plus a threshold. It is what makes an agent fail loudly and usefully rather than confidently.
