# L1 — Introduction to Agents and Their World

> **Thesis:** An agent is an LLM in a loop with tools and memory — and the interesting design
> question is not *what* an agent is, but *how much autonomy* you should give one.

## Why this chapter matters

It establishes the decomposition the rest of the book uses: **actions, memory, planning,
reasoning, evaluation, coordination**. Frameworks will churn; that decomposition will not, and
holding it clearly is what lets you evaluate any agent library on its merits.

Read it alongside [H6](../../04-ai-engineering-huyen/notes/ch06.md), which arrives at essentially
the same components from the direction of "how do I give the model context it lacks."

## Core concepts

### Defining an agent

Lanham's definition, and the one worth keeping: **an agent perceives its environment, reasons
about it, and acts on it to achieve a goal.**

For LLM agents that becomes:

```
loop:
    observe   → what is the current state?
    reason    → what should I do next?
    act       → call a tool
    (repeat until done, or until the budget runs out)
```

Compare a plain chatbot: one input, one output, no loop, no tools, no state. **The loop and the
tools are what make it an agent**, and everything else is refinement.

The critical clarification, worth stating explicitly because it prevents a lot of muddled
thinking: **the model does not execute anything.** It emits a structured request; your harness
validates and executes it and returns the result to the context
([A7](../../02-hands-on-llms-alammar/notes/ch07.md)). The LLM is the decision-maker; the harness
is the runtime, the security boundary, and everything else.

### Levels of autonomy

The most useful framing in the chapter, because it turns "should we build an agent?" into a
calibrated question rather than a binary:

| Level | Pattern | Human role | Example |
|---|---|---|---|
| 0 | Single call | Reads output | Summarize this |
| 1 | Fixed chain | Reads output | Extract → classify → format |
| 2 | **Routing** | Reads output | Model picks one of N fixed paths |
| 3 | **Tool use in a loop** | Approves consequential actions | ReAct-style research assistant |
| 4 | **Planning + execution** | Reviews the plan | Multi-step task completion |
| 5 | Fully autonomous, self-directed | Monitors | Rare, and rarely advisable |

**Most production value lives at levels 1–3.** Higher autonomy multiplies cost, latency, failure
surface, and the consequences of prompt injection
([H5](../../04-ai-engineering-huyen/notes/ch05.md)). The honest engineering question is: *what is
the lowest level that solves this problem?*

Anthropic's ["Building effective agents"](https://www.anthropic.com/engineering/building-effective-agents)
makes the same argument with the terms *workflow* (predetermined path) vs *agent* (model-directed
path) — worth reading alongside this chapter.

### Why agents now

Three things had to arrive together: models good enough to choose tools reliably, **function
calling** as a first-class typed interface rather than text parsing, and long-enough context to
hold a trajectory. None of those existed in usable form before roughly 2023.

### The honest state of things

Lanham is enthusiastic; the roadmap's position, which you should hold while reading, is more
measured:

- **Reliability compounds downward.** Ten steps at 95% is ~60% end to end
  ([H6](../../04-ai-engineering-huyen/notes/ch06.md)).
- **The dangerous failure is not a wrong answer** — it is a loop, a runaway bill, or a confidently
  wrong write action.
- **Most successful "agents" are constrained workflows.** One or two model decision points inside
  a deterministic scaffold. That constraint is a feature, not a compromise.
- **Evaluation is harder than for any other LLM system**, because you must evaluate a trajectory
  ([L10](ch10.md)).

None of that argues against building agents. It argues for building them with the evaluation
discipline from Phase 7 already in hand — which is exactly why this book comes last.

## Key code

```python
# The smallest thing that is genuinely an agent
def agent(task, tools, max_steps=10):
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):              # the cap is not optional
        response = model(messages, tools=tools)
        messages.append(response.message)
        if not response.tool_calls:            # no tool wanted => done
            return response.content
        for call in response.tool_calls:
            result = dispatch(call)            # YOUR code executes, not the model's
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": str(result)})
    return "max steps exceeded"
```

Twenty lines. Everything in the remaining ten chapters is making each of those lines robust.

## Gotchas

- **Calling a fixed chain an agent.** If the path is predetermined, it is a workflow. That is
  usually better — but be honest about what you built.
- **Reaching for level 5 autonomy.** Ask what the lowest level that works is.
- **Believing the model executes tools.** It emits a request; your harness executes and is
  therefore responsible for all validation and authorization.
- **No step cap.** The single most common agent incident.
- **No cost budget.** The second most common.
- **Evaluating only the final answer.** Efficiency and trajectory failures are invisible that way.
- **Adding agency because it is interesting.** Add it because the task genuinely needs dynamic
  decisions.

## Exercises

**Understand**
1. What distinguishes an agent from a chatbot, precisely?
2. Describe the six agent components and what each is responsible for.
3. Explain the autonomy levels and give an example of each.
4. Why do most production agents sit at levels 1–3?

**Build**
1. Write the 20-line agent loop above from scratch, with two tools. **No framework.** Everything
   later in the book will make more sense for having done this.
2. Take a task you would use an agent for and implement it at level 1 (fixed chain), level 2
   (routing), and level 3 (tool loop). Compare cost, latency, and success rate. **The comparison
   is the exercise** — often the fixed chain wins.
3. Instrument your loop to record the full trajectory: every step, tool call, result, token count,
   and cost. You need this for [L10](ch10.md).
