# L2 — Harnessing the Power of Large Language Models

> **Thesis:** Before you build an agent you need a model you can call reliably, locally or

## Core concepts

### What is genuinely different for agents

The parts of this chapter that are not review:

**1. Determinism matters more.** For a chatbot, sampling variation is texture. For an agent
choosing among tools, it is a different execution path — and a different bill. **Use temperature 0
for tool-selection calls**, and reserve higher temperature for generation steps where variety is
wanted. Many agent frameworks default to 0.7 for everything, which is a mistake.

**2. Structured output is not optional.** An agent's decision must be machine-parseable every
time. Use native function calling or constrained decoding
([A6](../../02-hands-on-llms-alammar/notes/ch06.md)); "respond in JSON" fails eventually, and when
it fails mid-loop you get a hard-to-diagnose crash rather than a bad sentence.

**3. Prompt caching pays much more.** Agents resend a growing history every step. The system
prompt and tool definitions are constant across every step of every run — put them **first** so
prefix caching hits ([H9](../../04-ai-engineering-huyen/notes/ch09.md)). For a 10-step agent this
is not a micro-optimization.

**4. Context grows within a single task.** Every observation appends. A 10-step agent can burn
through a context window on one task, which makes memory management
([L8](ch08.md)) a requirement rather than a nicety.

**5. Cost is multiplicative, not additive.** One chat turn is one call. One agent task is *n*
calls over a *growing* context, so cost scales roughly quadratically with step count. Model this
before you deploy.

### Choosing a model for an agent

Different criteria than for a chatbot:

| Criterion | Why it matters for agents |
|---|---|
| **Tool-calling reliability** | The core competency. Test it specifically. |
| **Structured output support** | Native schema enforcement beats parsing. |
| **Instruction following** | It must respect constraints across many turns. |
| **Long context** | Trajectories accumulate. |
| **Latency** | Multiplied by step count — a 2 s model is 20 s over 10 steps. |
| **Cost** | Multiplied and then some. |

Note that **raw reasoning benchmark scores matter less than tool-calling reliability**. A model
that reasons brilliantly but emits malformed tool calls 5% of the time is unusable in a loop —
5% per step over 10 steps is a 40% failure rate.

`[framework-specific]` The chapter's OpenAI-API specifics generalize; every major provider now
offers equivalent function calling. **MCP** (Model Context Protocol) has since emerged as a
vendor-neutral standard for exposing tools to models, and is worth knowing about.

### Local models for agents

Lanham covers running open models locally (LM Studio, Ollama, `llama.cpp`). For agent work this is
genuinely valuable: iterating on an agent loop against a paid API gets expensive fast, because
every debugging run is *n* calls.

The caveat: **small local models are noticeably worse at tool calling** than frontier models. Test
your loop against both. A pattern that works well is developing against a local model to shake out
harness bugs, then evaluating against the model you will actually ship.

```python
# Order the prompt so prefix caching can hit: constant content first.
# Over a 10-step agent run, this is real money.
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},   # constant across all runs
    *FEW_SHOT_EXAMPLES,                             # constant
    *conversation_history,                          # grows
    {"role": "user", "content": current_input},     # varies
]
```

```python
# Cost model an agent BEFORE deploying it: context grows every step
def estimate_agent_cost(base_tokens, tokens_per_step, steps, in_price, out_price):
    total_in = sum(base_tokens + tokens_per_step * i for i in range(steps))
    total_out = tokens_per_step * steps
    return total_in / 1e6 * in_price + total_out / 1e6 * out_price

# 10 steps, 2k system prompt, 500 tokens/step -> input grows quadratically
print(estimate_agent_cost(2000, 500, 10, in_price=3.0, out_price=15.0))
```

## Gotchas

- **temperature 0.7 for tool selection.** Non-deterministic execution paths and non-deterministic
  bills. Use 0.
- **Text-parsed tool calls.** Use native function calling or constrained decoding.
- **Variable content early in the prompt.** Kills prefix caching, and agents pay for it *n* times.
- **Not measuring tool-calling reliability specifically.** It is the agent-critical capability, and
  benchmark scores do not predict it.
- **Modeling cost as steps × single-call cost.** Context grows each step, so real cost is closer
  to quadratic.
- **Developing exclusively against a local small model.** It will hide tool-calling problems that
  appear in production, and vice versa. Test both.
- **Assuming context is unlimited.** One long task can exhaust the window.

## Exercises

**Understand**
1. Why should tool-selection calls use temperature 0?
2. Why does agent cost grow faster than linearly in step count?
3. Why does tool-calling reliability matter more than reasoning benchmark scores?

**Build**
1. Build a **tool-calling reliability benchmark**: 50 requests with known correct tool and
   arguments. Score three models on selection accuracy and argument validity. **This is a more
   useful measurement for agent work than any public benchmark**, and almost nobody has one.
2. Implement the cost estimator and validate it against a real 10-step run.
3. Measure prefix-cache savings: run the same 10-step agent with constant content first, then
   with it interleaved. Compare cost and TTFT.
4. Run the same agent loop against a frontier model and a local 7B. Catalogue where the small
   model's tool calls go wrong.

## Flashcards

<!-- card -->
Q: Why should agent tool-selection calls use temperature 0?
A: Sampling variation in a chatbot is texture; in an agent it is a different execution path, a different set of side effects, and a different bill. Reserve higher temperature for generation steps where variety is actually wanted.
<!-- /card -->

<!-- card -->
Q: Why does agent cost scale worse than linearly with step count?
A: Each step resends a context that has grown by the previous step's observation, so total input tokens grow roughly quadratically in steps — not steps × single-call cost.
<!-- /card -->

<!-- card -->
Q: Why does tool-calling reliability matter more than reasoning benchmarks for agents?
A: Errors compound per step. A model that emits malformed tool calls 5% of the time fails ~40% of 10-step tasks, no matter how well it reasons.
<!-- /card -->

<!-- card -->
Q: Why does prompt ordering matter more for agents than for chatbots?
A: An agent resends a growing history at every step, so a cacheable constant prefix (system prompt + tool definitions) is reused n times per task. Putting variable content first forfeits that saving repeatedly.
<!-- /card -->
