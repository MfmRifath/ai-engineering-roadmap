# L3 — Engaging GPT Assistants

> **Thesis:** Managed assistant platforms handle the tedious parts — state, file handling,
> retrieval, code execution — in exchange for control, portability, and observability.

## Why this chapter matters

**Skimmable, and the most dated chapter in the book.** `[framework-specific]` It covers OpenAI's
Assistants API and custom GPTs, both of which have moved substantially since publication — the
Assistants API has been superseded by newer agent primitives, and every major provider now offers
some managed equivalent.

What survives is the **build-vs-buy question for the agent runtime**, which is a decision you will
genuinely face.

## Core concepts

### What a managed assistant platform gives you

The recurring feature set, whichever vendor:

| Feature | What it saves you |
|---|---|
| **Persistent threads** | Conversation state management ([L8](ch08.md)) |
| **Built-in retrieval** | An entire RAG pipeline ([A8](../../02-hands-on-llms-alammar/notes/ch08.md)) |
| **Code interpreter** | A sandboxed execution environment |
| **File handling** | Upload, parse, chunk, index |
| **Managed tool loop** | The orchestration from [L1](ch01.md) |

That is a genuinely large amount of undifferentiated work.

### The trade

| You gain | You give up |
|---|---|
| Speed to first working version | Control over chunking, retrieval, and prompts |
| No infrastructure | Portability — you are locked to the vendor |
| Managed state | Observability into what actually happened |
| Vendor-maintained | Version stability ([H4](../../04-ai-engineering-huyen/notes/ch04.md)) |
| Lower initial cost | Predictable cost at scale |

**The observability row is the one that bites.** [H10](../../04-ai-engineering-huyen/notes/ch10.md)
insists on full traces — prompt version, retrieved chunks, tool calls, tokens. Managed platforms
typically expose a subset, which means when quality degrades you cannot tell whether retrieval
changed, the prompt template changed, or the model changed underneath you.

The **retrieval control** row matters almost as much. [A8](../../02-hands-on-llms-alammar/notes/ch08.md)
and [H6](../../04-ai-engineering-huyen/notes/ch06.md) established that chunking strategy and
reranking are where RAG quality is won. A managed retriever makes those decisions for you, and
usually will not tell you what it chose.

### A reasonable decision rule

**Use a managed platform when:** you are prototyping, retrieval quality requirements are modest,
you have no infrastructure team, and the vendor's model is the one you want anyway.

**Build your own when:** retrieval quality is a differentiator, you need full traces for
evaluation, you need to switch models or providers, cost at scale matters, or you have compliance
requirements about where data goes.

The pattern that works well in practice: **prototype on the managed platform to validate the use
case, then rebuild the pieces that turn out to be differentiating.** You usually discover that
only one or two components actually needed control.

### Custom GPTs and their descendants

The "no-code agent for a specific task" idea — a persona, some knowledge files, some actions — has
persisted across vendors even as the specific product changed. Its real value is as a
**requirements-gathering tool**: build the no-code version in an hour, put it in front of users,
learn what they actually want, then build the real thing.

## Key code

`[framework-specific]` The specific API here has changed enough that reproducing it would teach
you a deprecated interface. The durable version is the abstraction:

```python
# Abstract the runtime so "managed vs self-hosted" is a config choice, not a rewrite.
# This is the H10 gateway idea applied to the agent runtime.
class AgentRuntime(Protocol):
    def create_thread(self) -> str: ...
    def add_message(self, thread_id: str, content: str) -> None: ...
    def run(self, thread_id: str, tools: list[Tool]) -> RunResult: ...
    def get_trace(self, run_id: str) -> Trace: ...   # insist on this one

class ManagedRuntime(AgentRuntime): ...
class LocalRuntime(AgentRuntime): ...    # your own loop from L1
```

Writing that interface first is what makes the eventual migration a day rather than a quarter.

## Gotchas

- **Building on a managed platform without an abstraction layer.** Migration becomes a rewrite.
- **Accepting partial traces.** If you cannot see retrieved chunks and tool calls, you cannot
  debug or evaluate ([H10](../../04-ai-engineering-huyen/notes/ch10.md)).
- **Assuming managed retrieval is good enough.** It is a default chunking and retrieval strategy
  chosen without knowledge of your corpus.
- **Cost surprises at scale.** Managed platforms bundle retrieval, storage, and execution into
  pricing that is hard to model.
- **Vendor version drift.** The platform updates its internals and your quality changes with no
  action on your part.
- **Learning a deprecated API in detail.** Learn the pattern; check current docs for the interface.

## Exercises

**Understand**
1. What does a managed assistant platform actually do for you?
2. Which of the things you give up matters most, and why?
3. Give the decision rule for managed vs self-hosted agent runtime.

**Build**
1. Build the same simple agent twice: once on a managed platform, once with your own loop from
   [L1](ch01.md). Compare development time, cost per task, and — most importantly — **how much you
   can see about what happened**.
2. Write the `AgentRuntime` protocol above and implement both backends behind it.
3. Take a managed platform's built-in retrieval and compare its recall@5 against your own
   [p2](../../../projects/p2-rag-over-my-library/) pipeline on the same corpus and questions. The
   result tells you whether retrieval is a differentiator for you.

## Flashcards

<!-- card -->
Q: What do you give up by using a managed assistant platform?
A: Control over retrieval and prompts, portability (vendor lock-in), observability into what actually happened, version stability, and predictable cost at scale — in exchange for speed, managed state, and no infrastructure.
<!-- /card -->

<!-- card -->
Q: Which managed-platform tradeoff bites hardest in production?
A: Observability. Without full traces — prompt version, retrieved chunks, tool calls, tokens — you cannot tell whether a quality regression came from retrieval, the prompt template, or a model change underneath you.
<!-- /card -->

<!-- card -->
Q: What is a good pattern for using managed agent platforms?
A: Prototype on the managed platform to validate the use case, then rebuild only the components that turn out to be differentiating — usually retrieval and evaluation. Abstract the runtime behind an interface from day one so the migration is a day, not a quarter.
