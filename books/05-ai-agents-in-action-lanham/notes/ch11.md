# L11 — Agent Planning and Feedback

> **Thesis:** Plans go stale the moment execution begins, so the interesting engineering is not
> planning — it is **replanning**.

## Why this chapter matters

The final chapter, and it closes the loop on the whole roadmap: an agent that learns from feedback
is a system with a training signal, which is where you started in
[G1](../../01-hands-on-ml-geron/notes/ch01.md).

It is also where the RL vocabulary from [G18](../../01-hands-on-ml-geron/notes/ch18.md) pays off:
goals, actions, rewards, credit assignment. Agents are an RL problem where the policy happens to
be a language model.

## Core concepts

### Planning approaches

| Approach | How | Good when |
|---|---|---|
| **Reactive** (ReAct) | Decide one step at a time | The path is unpredictable |
| **Plan-then-execute** | Full plan up front, then run it | The structure is knowable |
| **Hierarchical** | Decompose into subtasks, plan each | Complex, decomposable goals |
| **Adaptive / replanning** | Plan, execute, revise as you learn | **Most real tasks** |

**The tradeoff.** Reactive planning adapts naturally but can wander — it has no global view and
can take a locally sensible path to nowhere. Plan-then-execute gives you a reviewable artifact and
bounded scope, but plans made without information you only get by executing are frequently wrong.

**Decoupling planning from execution** is the design move worth keeping
([H6](../../04-ai-engineering-huyen/notes/ch06.md)): generate the plan, **validate it**, then
execute. Validation catches invalid plans before they cost anything, and it gives a human
something reviewable for consequential tasks — a plan is far easier to review than a stream of
tool calls.

### Replanning — the actual problem

Plans fail. Concretely:

- A tool returns something the plan did not anticipate
- A step turns out to be impossible
- New information invalidates later steps
- The goal itself changes

**Triggers for replanning** — worth being explicit about, because implicit replanning is
indistinguishable from thrashing:

```
step failed          → replan from here
result contradicts an assumption the plan relied on → replan
progress has stalled (n steps, no advancement)      → replan
the goal changed                                    → replan from scratch
```

**Bound the replanning.** Cap replans per task. An agent that replans indefinitely is
[L6](ch06.md)'s loop wearing a smarter hat, and it costs considerably more per iteration.

**Preserve what you learned.** When replanning, carry forward the findings and the failed
approaches. Otherwise you replan into the same failure — the single most common replanning bug.
This is what [L6](ch06.md)'s scratchpad `attempted` list is for.

### Feedback

Three sources, and they differ in cost, volume, and reliability:

| Source | Example | Note |
|---|---|---|
| **Environmental** | Tool succeeded/failed, tests passed, API returned 200 | **Free, objective, immediate.** Use it most. |
| **Self-generated** | The agent critiques its own output | Cheap, biased ([L4](ch04.md)) |
| **Human** | Corrections, approvals, ratings | Expensive, sparse, authoritative |

**Environmental feedback is under-used and it is the best kind.** If the generated code compiles
and passes tests, that is ground truth — functional correctness
([H3](../../04-ai-engineering-huyen/notes/ch03.md)) delivered for free by the environment. **Design
tasks so environmental feedback exists**: ask for code you can run, queries you can execute,
structured output you can validate. That design choice buys you more than any evaluation
technique.

**Human feedback** should be captured with the trajectory attached, so you know *which step* was
wrong. A thumbs-down on a 10-step task tells you almost nothing without the trace
([L7](ch07.md)).

### Using feedback — the honest hierarchy

Ordered from most practical to least, which is the reverse of how exciting they sound:

1. **Immediate correction.** Feed the failure back in-context and retry. Reliable, cheap,
   effective. **This is where most of the value is.**
2. **Memory.** Store the correction so it is retrieved next time
   ([L8](ch08.md)). Corrections are the highest-value memories.
3. **Prompt improvement.** Aggregate failures, find the pattern, revise the prompt, run the eval
   suite ([L9](ch09.md)). Human-in-the-loop, and this is how real agents actually improve.
4. **Few-shot example selection.** Add corrected cases as examples.
5. **Fine-tuning.** Train on successful trajectories
   ([H7](../../04-ai-engineering-huyen/notes/ch07.md)). Real, but expensive and rarely the first
   answer.

> **The honest position on self-improving agents:** levels 1–3 work now and are how production
> agents get better. Fully autonomous self-improvement — an agent rewriting its own prompts and
> tools in a closed loop without human review — is a research direction, not a deployment
> strategy. It also has no error-correction mechanism: the agent evaluating its own improvements
> shares the blind spots that produced the failure.

### Credit assignment, again

Which of ten steps caused the failure? This is exactly
[G18](../../01-hands-on-ml-geron/notes/ch18.md)'s credit assignment problem, and the answers rhyme:

- **Step-level feedback** where you can get it — an intermediate result is checkable.
- **Trajectory comparison** — a successful and a failed run on the same task diverge somewhere,
  and that divergence point is informative.
- **Ablation** — replay the trajectory with one step corrected and see whether it succeeds.
- **LLM analysis** — give a judge the trace and ask where it went wrong
  ([L10](ch10.md)).

### Closing the loop

The pipeline that makes an agent improve over time, and none of the pieces are exotic:

```
production run
  → full trace ([L7](ch07.md))
  → outcome (environmental / human)
  → failures become eval cases ([L10](ch10.md), [H4](../../04-ai-engineering-huyen/notes/ch04.md))
  → corrections become memories ([L8](ch08.md))
  → patterns become prompt revisions ([L9](ch09.md))
  → re-run the eval suite → deploy
```

That loop is the whole book, and most of the roadmap, in seven lines. An agent without it does not
get better; it just gets older.

## Key code

```python
# Replanning that preserves what was learned — the most common bug is losing it
class Plan(BaseModel):
    goal: str
    steps: list[str]
    assumptions: list[str] = []
    replan_count: int = 0

def maybe_replan(plan: Plan, state, *, max_replans: int = 3) -> Plan:
    trigger = (
        "step_failed"      if state.last_step_failed else
        "assumption_broken" if state.contradicts(plan.assumptions) else
        "stalled"          if state.steps_without_progress >= 3 else
        None
    )
    if trigger is None:
        return plan
    if plan.replan_count >= max_replans:
        raise BudgetExceeded("replan limit reached")   # don't thrash

    new = planner.replan(
        goal=plan.goal,
        completed=state.completed_steps,
        findings=state.findings,        # carry knowledge forward
        failed=state.failed_approaches, # ...and mistakes, so we don't repeat them
        reason=trigger,
    )
    new.replan_count = plan.replan_count + 1
    return new
```

# Environmental feedback is free ground truth — design tasks so it exists
def execute_with_feedback(step, tools):
    result = dispatch(step.tool_call, tools)
    return Feedback(
        succeeded=result.ok,
        signal=result.error or "ok",
        # These are objective, immediate, and cost nothing to obtain

# Corrections are the highest-value memories (L8)
def record_correction(run_id: str, step: int, correction: str, memory_store):
    memory_store.write(Memory(
        kind="procedural",
        content=f"When doing this kind of task: {correction}",
        importance=0.9,                 # corrections outrank ordinary observations
        source_run_id=run_id,
    ))
    eval_suite.add_case(from_run(run_id, expected=correction))   # and a regression test

## Gotchas

- **Replanning without carrying forward findings.** You replan straight into the same failure.
- **No replan cap.** Thrashing, at higher cost per iteration than a plain loop.
- **Implicit replanning.** Without explicit triggers you cannot tell adaptation from confusion.
- **Ignoring environmental feedback.** It is free, objective, and immediate — and most systems
  only look at the final answer.
- **Human feedback without the trajectory.** A thumbs-down on a 10-step task is nearly
  information-free.
- **Jumping to fine-tuning.** Levels 1–3 capture most of the value at a fraction of the cost.
- **Autonomous self-improvement without review.** No error-correction mechanism; the agent shares
  the blind spots that caused the failure.
- **Not turning failures into eval cases.** Then you fix it once and regress it later.
- **Plans that cannot be validated.** If a plan is not checkable before execution, decoupling
  planning from execution buys you nothing.

## Exercises

**Understand**
1. Why is replanning the harder problem than planning?
2. List explicit replanning triggers.
3. Why is environmental feedback the most valuable kind?
4. Why is autonomous self-improvement not a deployment strategy?
5. How does agent credit assignment mirror the RL version?

**Build**
1. Implement plan-then-execute with **validation before execution**. Compare success rate and cost
   against your reactive [L6](ch06.md) loop on the same tasks.
2. Add replanning with explicit triggers, a cap, and preserved findings. **Then remove the
   preserved findings and watch it replan into the same failure** — that contrast is the lesson.
3. Design a task with environmental feedback (generate code that must pass tests) and one without
   (write a summary). Compare how much easier the first is to improve.
4. Capture human feedback with the trajectory attached. Use trajectory comparison to localize which
   step caused each failure.
5. **Close the loop end to end** for [p5](../../../projects/p5-agent-platform/): trace → outcome →
   eval case → memory → prompt revision → re-run evals. Run it for a week of real usage and
   measure whether the agent actually improved.

## Flashcards

<!-- card -->
Q: Why is replanning harder and more important than planning?
A: Plans are made without information you only obtain by executing, so they go stale immediately — a tool returns something unexpected, a step proves impossible, or new information invalidates later steps. The engineering is in detecting that and revising.
<!-- /card -->

<!-- card -->
Q: What are the explicit triggers for replanning?
A: A step failed; a result contradicts an assumption the plan relied on; progress has stalled for n steps; or the goal changed. Making these explicit is what distinguishes adaptation from thrashing.
<!-- /card -->

<!-- card -->
Q: What is the most common replanning bug?
A: Replanning without carrying forward findings and failed approaches — so the new plan walks straight back into the same failure. Preserve both.
<!-- /card -->

Q: Why is environmental feedback the most valuable kind?
A: It is free, objective, and immediate — the code compiled, the tests passed, the API returned 200. It is functional correctness delivered by the environment. Design tasks so it exists: ask for code you can run or structured output you can validate.
<!-- /card -->

<!-- card -->
Q: What is the practical hierarchy for using agent feedback?
A: (1) Immediate in-context correction and retry — where most value is; (2) store the correction as memory; (3) aggregate failures into prompt revisions, with eval suite; (4) few-shot example selection; (5) fine-tuning on successful trajectories. Most teams should stop at 3.
