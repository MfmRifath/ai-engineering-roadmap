# L8 — Understanding Agent Memory and Knowledge

> **Thesis:** Long-term agent memory is RAG with a write path — and the write path is the part
> nobody designs carefully.

## Why this chapter matters

Memory is what separates an agent that helps you once from one that gets better at helping you.
And the reframing above is the thing to take away: once you see memory as retrieval plus writing,
every design question becomes one you already know how to answer from
[A8](../../02-hands-on-llms-alammar/notes/ch08.md) and
[H6](../../04-ai-engineering-huyen/notes/ch06.md).

What is genuinely *new* here is the write side: **what to store, when, and how to handle
contradiction and decay.** Retrieval is a solved-ish problem; memory hygiene is not.

## Core concepts

### The memory taxonomy

Lanham borrows from cognitive science, and the mapping is useful:

| Type | Contains | Implementation |
|---|---|---|
| **Sensory** | Immediate input | The current message |
| **Short-term / working** | The current task | Context window, scratchpad ([L6](ch06.md)) |
| **Long-term semantic** | Facts, knowledge | Vector store + retrieval |
| **Long-term episodic** | Past events and interactions | Event log + retrieval |
| **Procedural** | How to do things | System prompt, tools, learned examples |

The distinction that matters most in practice is **semantic vs episodic**:

- Semantic: *"The user prefers Python."* Timeless facts.
- Episodic: *"On 3 March the user asked about deployment and we recommended Docker."* Events with
  timestamps.

They need different retrieval. Semantic memory wants deduplication and conflict resolution;
episodic memory wants recency weighting and time-range filtering. Conflating them produces a store
where an outdated preference and a current one look identical.

### The write path — where the real design is

**What to store.** Not everything. Storing every message makes retrieval worse (noise dominates)
and costs more. Candidates worth storing:

- Explicit user preferences and constraints
- Corrections ("no, I meant X") — **the highest-value memories**, because they encode a mistake
  you should not repeat
- Task outcomes and what worked
- Stable facts about the user's world

**When to write.** Three strategies:

| Strategy | How | Tradeoff |
|---|---|---|
| **Every turn** | Store everything | Noisy, expensive, degrades retrieval |
| **On signal** | Store when the user states a preference or corrects | Cheap; misses implicit information |
| **Reflection** | Periodically summarize a session into durable memories | Best quality, extra cost, some lag |

**Reflection** is the technique worth knowing: after a session, prompt the model to extract what
should be remembered. It is dramatically better than storing raw turns, because it produces
memories written *for retrieval* rather than transcripts.

**Contradiction.** The problem nobody plans for. The user said they prefer Python in March and Go
in June. Options: version memories with timestamps and prefer recent; explicitly detect and
supersede on write; or store both and let the model reason about the conflict at read time.
**Silently keeping both without timestamps is the failure mode** — retrieval returns a
contradiction and the model picks arbitrarily.

**Forgetting.** Memory that only grows degrades: retrieval quality falls as the store fills with
stale and irrelevant entries. Deliberate strategies: TTL on time-sensitive facts, relevance decay,
explicit user deletion (which is also a privacy requirement), and consolidation of related
memories into summaries.

### The read path

This is RAG ([A8](../../02-hands-on-llms-alammar/notes/ch08.md),
[H6](../../04-ai-engineering-huyen/notes/ch06.md)), with agent-specific adjustments:

- **Query construction matters more.** For memory, the "query" is often the current conversation
  state, not a user question. What you embed determines what you find.
- **Recency weighting.** Combine semantic similarity with age — a common formula is
  `score = α·similarity + β·recency + γ·importance`.
- **Retrieve less than you think.** 3–5 memories. More is distraction
  ([H6](../../04-ai-engineering-huyen/notes/ch06.md)).
- **Attribute memories in the prompt.** "You previously learned: X (2026-03-14)" lets the model
  reason about staleness and lets the user correct it.

### Knowledge vs memory

Worth keeping separate, because they have different update paths and different trust levels:

- **Knowledge** — documentation, product data, shared reference material. Curated, shared across
  users, updated by a pipeline.
- **Memory** — what this agent learned from this user. Per-user, written by the agent, and
  **should be user-inspectable and user-deletable**.

Mixing them in one store causes real problems: per-user memories leak across users, and corrections
to shared knowledge get overwritten by individual sessions. Keep separate stores with separate
access controls.

**Privacy.** Agent memory is personal data. It needs retention policy, deletion, and access
control by default, not as a later feature.

## Key code

```python
# Memory as a typed record — the write path deserves a schema
class Memory(BaseModel):
    id: str
    user_id: str
    kind: Literal["semantic", "episodic", "procedural"]
    content: str
    importance: float = 0.5
    created_at: datetime
    last_accessed: datetime
    superseded_by: str | None = None      # explicit contradiction handling
    source_run_id: str | None = None      # traceable back to L7's trace
```

```python
# Retrieval scoring: similarity alone is wrong for memory
def score(memory: Memory, query_emb, now: datetime,
          a: float = 0.6, b: float = 0.25, c: float = 0.15) -> float:
    if memory.superseded_by:
        return -1.0                                   # never retrieve superseded memories
    similarity = cosine(embed(memory.content), query_emb)
    age_days = (now - memory.created_at).days
    recency = 0.99 ** age_days                        # gentle exponential decay
    return a * similarity + b * recency + c * memory.importance
```

```python
# Reflection: extract durable memories from a session rather than storing transcripts
REFLECT = """Review this conversation and extract facts worth remembering long term.

Store ONLY: stated preferences, corrections the user made, constraints, and
stable facts about their situation. Do NOT store the conversation itself,
one-off questions, or anything already known.

For each, output: kind (semantic|episodic), content, importance (0-1).
If nothing is worth storing, return an empty list.

Conversation:
{conversation}"""
```

```python
# Attribute memories so the model — and the user — can judge staleness
def render_memories(memories: list[Memory]) -> str:
    lines = [f"- {m.content} (learned {m.created_at:%Y-%m-%d})" for m in memories]
    return ("Things you have previously learned about this user:\n"
            + "\n".join(lines)
            + "\nIf any of these appear outdated or contradicted, prefer the newer "
              "information and say so.")
```

## Gotchas

- **Storing every message.** Noise dominates retrieval and cost grows unboundedly.
- **No contradiction handling.** Retrieval returns both the old and new preference and the model
  picks arbitrarily.
- **No timestamps.** You cannot resolve conflicts or reason about staleness.
- **Memory that only grows.** Retrieval quality decays. Implement forgetting deliberately.
- **Mixing per-user memory with shared knowledge.** Leakage across users and overwritten
  corrections.
- **Similarity-only retrieval.** Recency and importance matter for memory in a way they do not for
  document search.
- **Retrieving 20 memories.** Distraction. Retrieve 3–5.
- **Unattributed memories in the prompt.** The model cannot judge staleness and the user cannot
  correct it.
- **No deletion path.** Users must be able to see and remove what an agent remembers about them.
- **Treating memory as a feature rather than personal data.** Retention and access control from
  day one.

## Exercises

**Understand**
1. In what precise sense is agent memory "RAG with a write path"?
2. Semantic vs episodic memory — why do they need different retrieval?
3. Name three strategies for handling contradictory memories.
4. Why does memory that only grows get worse?

**Build**
1. Build a memory store with the schema above: write, retrieve with combined scoring, and
   supersede. Wire it into your agent from [L6](ch06.md).
2. Implement **reflection** — extract durable memories from a session — and compare retrieval
   quality against storing raw turns. The gap is usually large.
3. Construct a contradiction: state a preference, then contradict it later. Verify your system
   resolves it rather than returning both.
4. Implement forgetting (TTL plus relevance decay) and measure retrieval quality on a store of
   1,000 memories with and without it.
5. Build a user-facing "what do you remember about me?" view with per-item deletion. **This is
   both a privacy requirement and the best memory-debugging tool you will have.**

## Flashcards

<!-- card -->
Q: In what sense is long-term agent memory just RAG?
A: The read path is identical — embed a query, retrieve relevant items, put them in context. What is new is the **write path**: deciding what to store, when, how to handle contradictions, and when to forget.
<!-- /card -->

<!-- card -->
Q: Semantic vs episodic memory — what's the difference and why does it matter?
A: Semantic is timeless facts ("the user prefers Python"); episodic is timestamped events ("on 3 March they asked about deployment"). They need different retrieval — semantic wants deduplication and conflict resolution, episodic wants recency weighting and time filtering.
<!-- /card -->

<!-- card -->
Q: What is reflection in agent memory?
A: Periodically prompting the model to extract what is worth remembering from a session, rather than storing raw turns. It produces memories written *for retrieval* instead of transcripts, and the quality difference is large.
<!-- /card -->

<!-- card -->
Q: How do you handle contradictory memories?
A: Timestamp everything and prefer recent; explicitly detect and mark superseded entries on write; or store both and let the model reason about the conflict. The failure mode is keeping both *without* timestamps, so retrieval returns a contradiction the model resolves arbitrarily.
<!-- /card -->

<!-- card -->
Q: Why must agent memory implement forgetting?
A: A store that only grows fills with stale and irrelevant entries, and retrieval quality degrades as noise crowds out signal. Use TTLs on time-sensitive facts, relevance decay, consolidation, and user-initiated deletion.
<!-- /card -->

<!-- card -->
Q: Why score memories on more than similarity?
A: For documents, relevance is mostly semantic. For memory, a recent or important item often beats a slightly more similar stale one — hence score = α·similarity + β·recency + γ·importance.
<!-- /card -->

<!-- card -->
Q: Why keep knowledge and memory in separate stores?
A: Knowledge is curated, shared across users, and updated by a pipeline. Memory is per-user, written by the agent, and must be user-inspectable and deletable. Mixing them leaks personal data across users and lets individual sessions overwrite shared corrections.
