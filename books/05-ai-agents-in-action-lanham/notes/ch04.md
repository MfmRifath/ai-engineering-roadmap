# L4 — Exploring Multi-Agent Systems

> **Thesis:** Multiple specialized agents can outperform one general agent — but the gain comes
> from *decomposition*, and you should check whether you can get the decomposition without the
> multiplication of cost.

## Why this chapter matters

Multi-agent systems are the most over-applied pattern in the field, and also genuinely right
sometimes. This chapter gives you the topologies and the vocabulary; the judgment about when to
use them is what you should extract.

## Core concepts

### Why multiple agents

The legitimate arguments:

1. **Specialization.** A focused system prompt and a small tool set outperform a general agent
   with thirty tools — tool-selection accuracy degrades with tool count
   ([H6](../../04-ai-engineering-huyen/notes/ch06.md)).
2. **Separation of concerns.** A researcher agent and a writer agent are separately testable and
   separately improvable.
3. **Diverse perspectives.** A critic agent reviewing a generator's output catches errors the
   generator will not — this is [G7](../../01-hands-on-ml-geron/notes/ch07.md)'s ensembling
   argument, and it works for the same reason: **the errors must be uncorrelated.**
4. **Parallelism.** Independent subtasks can genuinely run concurrently.

The costs, which are not small:

- **Cost multiplies.** Every agent is its own context and its own calls.
- **Latency adds** for sequential handoffs.
- **Errors compound across agents** as well as within them.
- **Debugging is much harder.** Which agent, at which turn, made the wrong call?
- **Context loss at handoffs.** What one agent knows, the next often does not.

> **The question to ask:** could one agent with better prompting and a smaller tool set do this?
> Frequently yes. Multi-agent architectures are sometimes a way of avoiding a clear problem
> decomposition rather than achieving one.

### Topologies

| Pattern | Structure | Good for | Watch out for |
|---|---|---|---|
| **Sequential / pipeline** | A → B → C | Clear stages (research → draft → edit) | Compounding error, latency |
| **Hierarchical** | Manager delegates to workers | Task decomposition | Manager becomes a bottleneck and a single point of failure |
| **Group chat** | Agents converse, a manager picks who speaks | Open-ended problems | Cost explosion, rambling, no termination |
| **Debate / critic** | Generator + critic loop | Quality-critical output | Diminishing returns after ~2 rounds |
| **Blackboard** | Shared state all agents read/write | Loosely coupled work | Contention, staleness |

**Group chat is the seductive one and the most dangerous.** It demos beautifully and, without hard
turn caps and clear termination conditions, it produces long, expensive conversations that
converge on nothing. If you use it, cap turns aggressively.

**The critic pattern is the reliably valuable one.** Generate, then critique against explicit
criteria, then revise. Two rounds captures most of the gain; more rarely helps. It is
[H3](../../04-ai-engineering-huyen/notes/ch03.md)'s LLM-as-judge applied inside the system rather
than for offline evaluation — which means it inherits the same biases, and a critic that always
says "looks good" is worse than no critic.

### Communication and roles

**Message passing** — structured, typed, explicit. Preferable, because it is inspectable.
**Shared state** — a blackboard all agents access. Simpler, but concurrent writes create
inconsistency.

**Role design** matters as much as prompt design:
- A **specific** role beats a vague one ("Extract structured financial data" beats "You are a
  helpful analyst").
- Give each role only the tools it needs — this is least privilege
  ([H5](../../04-ai-engineering-huyen/notes/ch05.md)) and it also improves selection accuracy.
- Define **termination conditions** explicitly. Who decides the task is done, and how?

`[framework-specific]` The chapter uses AutoGen and CrewAI. Both remain in use; LangGraph and
provider-native orchestration are now common alternatives. The topologies above are what transfer.

## Key code

```python
# Sequential pipeline: the simplest multi-agent pattern, and often sufficient.
# Note that "multi-agent" here is really just three prompts in a row.
def pipeline(task, agents):
    output = task
    trace = []
    for agent in agents:
        output = agent.run(output)
        trace.append({"agent": agent.name, "output": output})   # inspectable
    return output, trace

result, trace = pipeline(brief, [researcher, writer, editor])
```

```python
# Critic loop: the reliably valuable pattern.
# Two rounds captures most of the gain — cap it.
def generate_with_critique(task, generator, critic, max_rounds=2):
    draft = generator.run(task)
    for _ in range(max_rounds):
        critique = critic.run(draft, criteria=CRITERIA)   # explicit criteria, not "is this good?"
        if critique.approved:
            break
        draft = generator.run(task, feedback=critique.feedback)
    return draft
```

```python
# Group chat needs a hard cap or it will not terminate
def group_chat(task, agents, manager, max_turns=8):
    history = [{"role": "user", "content": task}]
    for turn in range(max_turns):                 # NOT optional
        speaker = manager.select_speaker(agents, history)
        if speaker is None:                       # explicit termination
            break
        history.append(speaker.respond(history))
    return manager.summarize(history)
```

## Gotchas

- **Multi-agent as a substitute for decomposition.** Try one well-scoped agent first.
- **Group chat with no turn cap.** It will not terminate on its own.
- **No explicit termination condition.** Someone must decide when the task is done.
- **Context loss at handoffs.** Decide deliberately what each agent passes on; "everything" is
  expensive and "the final answer only" loses reasoning.
- **A critic with vague criteria.** "Is this good?" produces "yes." Give it a rubric
  ([H4](../../04-ai-engineering-huyen/notes/ch04.md)).
- **More than two critique rounds.** Diminishing returns, sometimes negative.
- **Correlated agents.** Same model, same prompt style, same blind spots — the ensembling benefit
  requires uncorrelated errors.
- **No per-agent tracing.** You cannot debug a multi-agent failure without knowing which agent did
  what.
- **Unbounded total cost.** Budget the *system*, not each agent.

## Exercises

**Understand**
1. Give four legitimate reasons for multiple agents and four costs.
2. Which topology is most dangerous and why?
3. Why does the critic pattern require uncorrelated errors to help?
4. What must every multi-agent system define explicitly?

**Build**
1. Solve one task three ways: a single agent with all tools, a sequential pipeline, and a
   generator/critic loop. Compare quality, cost, and latency. **Very often the single agent wins**
   — that result is the lesson.
2. Implement the critic loop with an explicit rubric. Measure quality gain per round for rounds
   1–4 and find where it flattens.
3. Build a group chat with a turn cap and a termination condition. Then remove the cap and watch
   what happens (with a hard cost limit in place).
4. Instrument per-agent tracing and inject a deliberate failure into one agent. Confirm you can
   localize it from the trace alone.

## Flashcards

<!-- card -->
Q: Give four legitimate reasons to use multiple agents.
A: Specialization (focused prompts and small tool sets outperform one general agent with many tools), separation of concerns (separately testable), diverse perspectives (a critic catches what a generator misses), and genuine parallelism on independent subtasks.
<!-- /card -->

<!-- card -->
Q: What is the main question to ask before building a multi-agent system?
A: Could one agent with better prompting and a smaller tool set do this? Multi-agent architectures are frequently a way of *avoiding* a clear problem decomposition rather than achieving one — and they multiply cost, latency, and debugging difficulty.
<!-- /card -->

<!-- card -->
Q: Why is the group-chat topology the most dangerous?
A: It demos beautifully but without hard turn caps and explicit termination conditions it produces long, expensive conversations that converge on nothing.
<!-- /card -->

<!-- card -->
Q: Why does the critic pattern require uncorrelated errors?
A: It is ensembling. If the critic shares the generator's model, prompt style, and blind spots, it will approve exactly the errors the generator makes. Diversity of error is the entire mechanism.
<!-- /card -->

<!-- card -->
Q: How many critique rounds are worth running?
A: About two. Most of the quality gain arrives in the first two rounds and further rounds show diminishing — occasionally negative — returns.
<!-- /card -->
