# L7 — Assembling and Using an Agent Platform

> **Thesis:** Once you have more than one agent, the reusable infrastructure — registries,
> routing, state, tracing — is the platform, and building it deliberately beats accumulating it
> accidentally.

## Why this chapter matters

Lanham builds **Nexus**, his own agent platform, across this chapter. `[framework-specific]` The
specific implementation is less important than the **component inventory**: what a platform must
provide, whichever one you use or build.

Read it as a checklist for evaluating agent frameworks — and note how closely it parallels
[H10](../../04-ai-engineering-huyen/notes/ch10.md)'s production architecture. The two are the same
system viewed from different ends.

## Core concepts

### What a platform must provide

| Component | Responsibility |
|---|---|
| **Agent registry** | Definitions, personas, capabilities, versions |
| **Tool registry** | Schemas, permissions, per-context scoping ([L5](ch05.md)) |
| **Model gateway** | Provider abstraction, routing, fallback ([H10](../../04-ai-engineering-huyen/notes/ch10.md)) |
| **Orchestration** | The loop, topologies, termination ([L4](ch04.md)) |
| **State / memory** | Threads, scratchpads, long-term storage ([L8](ch08.md)) |
| **Observability** | Traces, metrics, cost accounting |
| **Evaluation** | Trajectory scoring, regression suites ([L10](ch10.md)) |
| **Interface** | Chat UI, API, or embedded |

If a framework you are evaluating does not have a clear answer for **observability** and
**evaluation**, treat that as disqualifying. Everything else you can build around; those two you
cannot retrofit, and they are the ones that determine whether you can operate the system.

### Observability is the platform's real job

The single most valuable thing a platform gives you. Every run should produce a **complete
trace**:

```
run_id, agent_version, model+version, prompt_version
  step 0: input, tool_calls[], results[], tokens, cost, latency
  step 1: ...
  outcome: success | failure | timeout | budget, final answer
```

Why this is non-negotiable for agents specifically: a chatbot failure is one call you can
reproduce. An agent failure is a *trajectory* — the wrong tool at step 3 caused the wrong result
at step 4 which caused the loop at steps 5 through 9. **Without the full trace you are guessing**,
and with it every failed run becomes an eval case
([H4](../../04-ai-engineering-huyen/notes/ch04.md)).

This is the same argument as [H10](../../04-ai-engineering-huyen/notes/ch10.md), and it is why
that chapter's warning about managed platforms exposing partial traces
([L3](ch03.md)) is worth taking seriously.

### Agent definitions as configuration

Separating agent definitions from code makes them versionable, reviewable, and diffable — the same
argument as prompts-are-code ([H5](../../04-ai-engineering-huyen/notes/ch05.md)):

```yaml
name: research_assistant
version: 4
model: claude-sonnet-4-5
temperature: 0
max_steps: 10
max_cost_usd: 0.50
tools: [search_docs, fetch_url, summarize]
system_prompt_ref: prompts/research/v4.md
termination: no_tool_calls | max_steps | budget
```

The payoff is that a behaviour change becomes a reviewable diff, and every trace can record
exactly which version produced it.

### Interfaces and the choice you are actually making

Chat is the default and it is often wrong. A chat interface implies open-ended capability, which
sets user expectations your agent cannot meet. **A constrained interface — a form, a button, a
specific action — sets accurate expectations and narrows the input distribution**, which improves
reliability for free.

This connects back to [L1](ch01.md)'s autonomy levels: the interface should advertise the autonomy
level you actually built.

### Deployment concerns

- **Long-running tasks.** Agent runs take minutes. That means async execution, job queues, and
  status polling — not a synchronous HTTP request.
- **Streaming intermediate state.** Users need to see progress or they assume it hung. Streaming
  tool calls and partial results is a large UX win.
- **Concurrency and rate limits.** Many agents × many steps hits provider limits fast.
- **Cost attribution.** Per user, per agent, per task — you need this before the invoice, not
  after.
- **Graceful shutdown.** In-flight runs need to checkpoint or fail cleanly.

## Key code

```python
# The trace is the platform's core artifact. Design it first.
@dataclass
class StepTrace:
    step: int
    messages_in: list[dict]
    tool_calls: list[dict]
    tool_results: list[str]
    tokens_in: int
    tokens_out: int
    cost_usd: float
    latency_ms: float

@dataclass
class RunTrace:
    run_id: str
    agent_name: str
    agent_version: int
    model: str
    prompt_version: str
    task: str
    steps: list[StepTrace]
    outcome: Literal["success", "failure", "timeout", "budget", "max_steps"]
    final_answer: str | None

    @property
    def total_cost(self) -> float:
        return sum(s.cost_usd for s in self.steps)

    def to_eval_case(self) -> dict:
        """Every failed run becomes a regression test."""
        return {"task": self.task, "expected_outcome": "success",
                "trace": self, "added": date.today().isoformat()}
```

```python
# Agent definitions as versioned config, not code
def load_agent(name: str, version: int | None = None) -> Agent:
    cfg = registry.get(name, version)          # version=None -> latest
    return Agent(
        model=gateway.get(cfg.model),
        tools=[tool_registry.get(t) for t in cfg.tools],
        system_prompt=prompts.get(cfg.system_prompt_ref),
        guards=Guards(max_steps=cfg.max_steps, max_cost=cfg.max_cost_usd),
        version=cfg.version,                   # recorded in every trace
    )
```

## Gotchas

- **Building a platform before you need one.** One agent does not need a registry. Build it when
  the third one arrives.
- **Adopting a framework without checking observability.** The thing you cannot retrofit.
- **Traces that omit tool results.** The most common gap, and it is where failures live.
- **Agent definitions in code.** Unversioned behaviour changes are unattributable.
- **Synchronous HTTP for agent runs.** They take minutes. Use async with status.
- **No progress streaming.** Users assume it hung and retry, doubling your cost.
- **No cost attribution.** You will find out at the end of the month.
- **A chat interface for a narrow agent.** It promises capability you did not build.

## Exercises

**Understand**
1. List the eight platform components and what each owns.
2. Why is observability the component you cannot retrofit?
3. Why does a chat interface sometimes hurt reliability?
4. Why must agent runs be asynchronous?

**Build**
1. Implement `RunTrace` and `StepTrace` and instrument your [L6](ch06.md) loop to emit them.
   **Then run 20 tasks and see what you can learn from the traces alone.**
2. Move your agent definitions into YAML with versions. Record the version in every trace.
3. Add `to_eval_case()` and build a regression suite from your failed runs
   ([H4](../../04-ai-engineering-huyen/notes/ch04.md)).
4. Make one agent run asynchronous with a job ID, status polling, and streamed intermediate steps.
5. Evaluate one agent framework against the eight-component checklist. Note specifically what its
   traces do and do not contain.
