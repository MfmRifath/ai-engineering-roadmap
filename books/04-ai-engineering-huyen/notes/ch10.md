# H10 — AI Engineering Architecture and User Feedback

> **Thesis:** Every production LLM system converges on the same five-step architecture, and
> knowing the order in advance saves you a rewrite.

## Why this chapter matters

The synthesis chapter. It takes everything from the previous nine and assembles it into a system
you could actually operate, and the **incremental order** is the valuable part: each step is added
only when the previous one is not enough.

The user-feedback section is also the most neglected topic in the field. Feedback is the only
renewable source of evaluation data you have.

## Core concepts

### The five steps, in order

Start with the simplest thing — a model behind an API — and add only what you need.

**Step 1 — Enhance context.** RAG, tools, memory ([H6](ch06.md)). Most quality problems are
context problems, so this comes first. Before you reach for a better model, ask whether the model
had what it needed.

**Step 2 — Put in guardrails.** Two directions, and both are required:

| Direction | Protects against | Examples |
|---|---|---|
| **Input** | Malicious or invalid input | PII detection, injection detection, topic/scope filtering, rate limits |
| **Output** | Bad or unsafe generations | Toxicity, PII leakage, schema validation, factuality checks, refusal handling |

Guardrails add latency, and there is a real tradeoff between blocking output until it is checked
and streaming it for responsiveness. Streaming plus post-hoc checking means bad content can be
briefly visible; blocking means slower perceived response. Decide deliberately, per surface.

**Step 3 — Add a model router and gateway.**

- **Router** — send different requests to different models. Cheap model for easy queries,
  expensive one for hard queries. Often the single largest cost saving available, because most
  traffic is easy.
- **Gateway** — one interface to many providers. Centralizes auth, rate limiting, fallback,
  retries, logging, and cost accounting.

The gateway is also your **defense against provider drift and deprecation**
([H4](ch04.md)). Without it, a provider change is a code change in fifty places.

**Step 4 — Reduce latency with caches.**

| Cache | Key | Note |
|---|---|---|
| **Exact** | The full prompt | Trivial, safe, surprisingly effective |
| **Semantic** | Embedding similarity | Powerful and **risky** — similar ≠ same |
| **Prefix / KV** | Shared prompt prefix | Provider-side; free if you order the prompt correctly ([H9](ch09.md)) |

Semantic caching deserves the warning. "What is our refund policy for EU customers?" and "What is
our refund policy for US customers?" are highly similar and have different answers. Set the
threshold conservatively and evaluate the cache's hit *correctness*, not just its hit rate.

**Step 5 — Add agent patterns.** Loops, tools, planning ([H6](ch06.md)). Last, because agents
multiply cost, latency, and failure surface. Add them when the workflow genuinely requires
dynamic decisions, not because they are interesting.

### Monitoring and observability

What to track, grouped by what it tells you:

- **Quality** — eval scores on sampled traffic, user feedback signals, refusal and fallback rates.
- **Cost** — per request, per user, per feature. Detect the runaway before the invoice does.
- **Latency** — TTFT, TPOT, end-to-end, at p50/p95/p99 ([H9](ch09.md)).
- **Reliability** — error rates, timeouts, provider failures, retry rates.
- **Drift** — input distribution shift, output length shift, embedding-space shift.

**Log the full trace**: prompt version, model and version, retrieved chunks, tool calls, tokens,
cost, latency, and the output. Without complete traces, production debugging is guesswork —
and every trace is a potential eval case.

> A useful discipline: **every production failure becomes a test case** in the
> [H4](ch04.md) eval set. That is how the eval set becomes the most valuable artifact you own.

### AI pipeline orchestration

As systems grow into multi-step pipelines, you need retries, timeouts, fallbacks, parallelism,
and observability across steps. Whether you use a framework or your own code, the requirements
are the same — and Huyen's guidance is to choose based on **observability and debuggability**,
not on the elegance of the DSL.

### User feedback — the neglected asset

**Why it matters more here than in classical ML:** you rarely have ground-truth labels for
open-ended output, so user signals are your main renewable source of evaluation data.

**Explicit feedback** — thumbs up/down, ratings, corrections, flags. Sparse, biased toward
extremes (people rate when angry or delighted), and low-volume.

**Implicit feedback — much richer, and mostly ignored:**

| Signal | Suggests |
|---|---|
| Regeneration / retry | The answer was unsatisfactory |
| Rephrasing the question | Misunderstood |
| Copying the output | It was useful |
| Early conversation abandonment | Failure |
| Continuing the conversation | Engagement (or confusion — check which) |
| Editing before use | Partially useful |
| Accepting a suggestion (code completion) | Direct quality signal |

**Feedback design principles:**
- Make it **low-friction** — one click, in context.
- Ask **at the right moment** — right after the output, not in a survey later.
- Capture **why**, not just the rating, when you can.
- **Close the loop** — show that feedback did something, or people stop giving it.

**Limitations to hold onto:**
- **Selection bias.** Only certain users give feedback, and usually at the extremes.
- **Preference ≠ correctness.** Users prefer confident, agreeable, verbose answers. Optimizing
  directly for feedback can make the system *less* truthful — the reward-hacking argument from
  [H2](ch02.md), one layer up.
- **Feedback loops.** The system shapes the behaviour it then measures.

### The epilogue

Huyen's closing point deserves repeating: the field moves fast, but the **discipline** does not.
Evaluation, data quality, systems thinking, and clear-eyed measurement outlast any model
generation. That is the actual bet this roadmap makes.

## Key code

```python
# The gateway: one interface, so provider drift is a config change, not a refactor
class ModelGateway:
    def __init__(self, providers, router, cache, guardrails):
        self.providers, self.router = providers, router
        self.cache, self.guardrails = cache, guardrails

    def complete(self, request):
        self.guardrails.check_input(request)             # step 2, inbound

        if (hit := self.cache.get(request)) is not None: # step 4
            return hit

        model = self.router.select(request)              # step 3
        for attempt, provider in enumerate(self.providers.fallback_chain(model)):
            try:
                resp = provider.complete(request)
                break
            except ProviderError:
                if attempt == 2:
                    raise
        else:
            raise ProviderError("all providers failed")

        self.guardrails.check_output(resp)               # step 2, outbound
        self.cache.set(request, resp)
        self.trace(request, resp, model)                 # log EVERYTHING
        return resp
```

# Implicit feedback is richer than explicit and nearly free to collect
IMPLICIT = {
    "regenerated":     -1.0,   # the answer was unsatisfactory
    "rephrased":       -0.5,   # we misunderstood
    "abandoned":       -1.0,
    "copied_output":    1.0,   # strong positive
    "edited_then_used": 0.5,
    "accepted":         1.0,
}

def log_interaction(trace_id, signal):
    store.append({"trace_id": trace_id, "signal": signal,
                  "weight": IMPLICIT[signal], "ts": now()})

## Gotchas

- **Building the full architecture up front.** Add each step only when the previous is
  insufficient. Premature routers and caches are complexity with no payoff.
- **Semantic caching with a loose threshold.** Similar questions with different answers get the
  wrong cached response. Evaluate hit *correctness*.
- **Output-only guardrails.** Input guardrails catch injection and abuse before you pay for
  inference.
- **Incomplete traces.** Without prompt version, model version, retrieved chunks, and tool calls,
  you cannot reproduce a failure.
- **No cost alerting.** Runaway agent loops are discovered by invoice.
- **Optimizing directly for thumbs-up.** Users prefer confident and agreeable over correct.
- **Ignoring implicit feedback.** Regeneration and copy rates are higher-volume and less biased
  than explicit ratings.
- **Not closing the loop.** Feedback with no visible effect dries up.
- **No fallback chain.** Providers have outages. Yours should not.

## Exercises

**Understand**
1. Why is "enhance context" step 1 and "add agent patterns" step 5?
2. What makes semantic caching risky, and how do you evaluate it?
3. Give four implicit feedback signals and what each suggests.
4. Why can optimizing for user feedback reduce truthfulness?

**Build**
1. Implement a gateway with routing, fallback, caching, and full tracing for
   [p6](../../../projects/p6-production-llm-app/).
2. Add input and output guardrails and measure the added latency at p50 and p95. Decide whether
   to stream.
3. Build a router that sends easy queries to a small model and hard ones to a large one.
   **Measure the cost saving and any quality loss.** This is usually the largest single win.
4. Instrument implicit feedback (regeneration, copy, abandonment) and correlate it against your
   eval scores. Check whether the cheap signal predicts the expensive one.
5. Take ten production failures and turn each into an eval case ([H4](ch04.md)).
6. Evaluate a semantic cache: measure hit rate *and* the fraction of hits that returned a wrong
   answer.

Q: What are the five steps of Huyen's production LLM architecture, in order?
A: (1) Enhance context — RAG, tools, memory. (2) Add guardrails, input and output. (3) Add a model router and gateway. (4) Reduce latency with caches. (5) Add agent patterns. Each is added only when the previous is insufficient.
