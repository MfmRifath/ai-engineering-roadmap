# H3 — Evaluation Methodology

> **Thesis:** Open-ended output has no ground truth, so every evaluation method is a proxy with a
> characteristic failure mode — and the job is composing proxies whose failures do not overlap.

## Why this chapter matters

**Give this chapter double the time you planned.** Evaluation is the skill that separates people
who ship AI from people who demo it, and it is the most under-practiced discipline in the field.

The specific difficulty: everything you learned in
[G3](../../01-hands-on-ml-geron/notes/ch03.md) assumed a correct answer to compare against. For
"summarize this document" there are thousands of good answers and no list of them. Every technique
here is a way of working around that.

## Core concepts

### Why evaluating foundation models is hard

- **Open-ended output** — no single correct answer, so no exact comparison.
- **General purpose** — the model does everything, so no single benchmark covers it.
- **Benchmark saturation and contamination** — public benchmarks leak into training data. A high
  score may mean memorization. ([G2](../../01-hands-on-ml-geron/notes/ch02.md)'s test-set
  discipline, at internet scale, where you cannot control the training set.)
- **Human evaluation is slow and expensive**, and inter-rater agreement is often poor.

### Layer 1 — Language modeling metrics

**Entropy** measures average uncertainty. **Cross-entropy** measures how surprised your model is
by the true data. **Perplexity = exp(cross-entropy)** — the effective number of tokens being
chosen among ([R5](../../03-build-llm-from-scratch-raschka/notes/ch05.md)).

**Bits-per-character / bits-per-byte** normalize away tokenizer differences, which is what makes
cross-model comparison meaningful — perplexity depends on the tokenizer, so comparing perplexity
across models with different vocabularies is comparing nothing.

**What perplexity is good for:** detecting distribution shift, spotting data-quality problems,
tracking pretraining, identifying likely-memorized text (abnormally low perplexity).

**What it is not good for:** telling you whether a response is useful. A model can have excellent
perplexity and be unhelpful, and post-training typically *raises* perplexity while improving
usefulness.

### Layer 2 — Exact evaluation

**Functional correctness** — does the generated code pass the tests? Does the SQL return the
right rows? Does the JSON parse and validate?

**This is the gold standard where it applies.** Unambiguous, cheap, automatable, ungameable. The
strategic move in AI engineering is to **restructure tasks so functional correctness applies** —
ask for code that answers the question rather than the answer, ask for a structured extraction
you can validate rather than prose.

**Similarity against reference data**, weakest to strongest:

| Method | Catches | Misses |
|---|---|---|
| Exact match | Identical strings | Everything else |
| Lexical (BLEU, ROUGE) | n-gram overlap | Paraphrase |
| **Semantic (embedding similarity)** | Meaning | Factual errors that read plausibly |

That last cell matters: an embedding-similarity score is happy with a fluent, on-topic, **wrong**
answer. Semantic similarity measures topicality more than correctness.

### Layer 3 — AI as a judge

Use a model to evaluate a model. Practical, scalable, flexible — and the failure modes are
systematic and well-documented:

| Bias | What happens |
|---|---|
| **Position** | Prefers the first (or last) option presented |
| **Verbosity** | Longer answers score higher regardless of quality |
| **Self-preference** | Models favour their own outputs and style |
| **Inconsistency** | Same input, different score across runs |
| **Poor calibration** | "7/10" does not mean the same thing twice |

Mitigations that actually help:
- **Randomize position** and/or evaluate both orders and average.
- **Prefer comparison to scoring.** "Which is better, A or B?" is far more reliable than "rate
  this 0–100."
- **Give an explicit rubric with examples** for each score level.
- **Use a different model family** than the one being evaluated.
- **Validate the judge against human ratings.** Non-negotiable, and constantly skipped.

> Huyen's central point: **the judge is a model, so it needs evaluating too.** An unvalidated
> judge is an unexamined proxy you are now optimizing against — [H2](ch02.md)'s reward hacking,
> re-run at the evaluation layer.

A cheaper specialized judge (a fine-tuned classifier, or a small model) often beats a large
general one on cost *and* consistency for a narrow criterion.

### Layer 4 — Comparative evaluation

Rank models by pairwise preference rather than absolute scores — Elo-style, as in Chatbot Arena.

Why it works: **humans are much better at relative judgments than absolute ones.** "Is this a 7 or
an 8?" is nearly meaningless; "is A better than B?" is answerable.

Its limits:
- Gives you a **ranking, not a quality bar**. Best-of-a-bad-lot still ranks first.
- Needs many comparisons for statistical confidence; scales quadratically with candidates.
- Aggregate preference **hides per-task variation** — a model can win overall and lose badly on
  your task.
- Preference ≠ correctness. Users prefer confident, verbose, agreeable answers. Optimizing for
  preference can make a model *worse* on truthfulness.

## Key code

```python
# Comparative judging with position-bias control — evaluate BOTH orders
JUDGE = """Compare two responses to the same question.

Question: {question}

Response A: {a}
Response B: {b}

Which better satisfies these criteria: {rubric}?
Answer with exactly one of: A, B, TIE. Then give one sentence of reasoning."""

def compare(question, r1, r2, rubric):
    fwd = judge(JUDGE.format(question=question, a=r1, b=r2, rubric=rubric))
    rev = judge(JUDGE.format(question=question, a=r2, b=r1, rubric=rubric))
    # If flipping the order flips the verdict, the judge is guessing — record it as a tie.
    if fwd == "A" and rev == "B":
        return "r1"
    if fwd == "B" and rev == "A":
        return "r2"
    return "tie"
```

## Gotchas

- **Comparing perplexity across models with different tokenizers.** Meaningless. Use
  bits-per-byte.
- **Trusting a public benchmark score.** Contamination is pervasive. Build a private eval set.
- **Using an unvalidated LLM judge.** You are optimizing an unexamined proxy.
- **Absolute 0–100 judge scores.** Poorly calibrated and inconsistent. Use comparisons or a
  rubric with anchored examples.
- **Not controlling for position.** Evaluate both orders.
- **Ignoring verbosity bias.** Control for length, or you will select for waffle.
- **Semantic similarity as a correctness metric.** It rewards fluent, on-topic, wrong answers.
- **Optimizing for human preference.** Preference correlates with confidence and length more
  than with truth.
- **A single aggregate number.** Report per-category; aggregates hide the failures you care about.

## Exercises

**Understand**
1. Why is evaluating foundation models harder than evaluating a classifier?
2. What is perplexity useful for, and what is it useless for?
3. Name five biases of LLM judges and a mitigation for each.
4. Why are comparative evaluations more reliable than absolute scores?
5. Why can optimizing for human preference reduce truthfulness?

**Build**
1. **Build a 50-example evaluation set for a task you care about**, with reference answers. This
   is the single highest-value exercise in the book. Everything else depends on it.
2. Implement three evaluators for it — exact/functional, embedding similarity, and LLM judge.
   Correlate each against your own human ratings. **Learn which proxy you can trust.**
3. Demonstrate position bias: run the same comparison in both orders across 50 pairs and count
   disagreements.
4. Demonstrate verbosity bias: pad correct answers with irrelevant but fluent text and see if
   judge scores rise.
5. Compare a large general judge against a small specialized one on cost, latency, and agreement
   with your ratings.
