# R4 — Implementing a GPT Model from Scratch

> **Thesis:** A GPT is embeddings, a stack of identical blocks, and a linear head — and each block
> is just attention plus a feedforward network, each wrapped in a normalized residual connection.

## Why this chapter matters

This is where the parts become a model. By the end you have a 124M-parameter GPT-2 that runs and
generates text. The text will be terrible, because it is untrained — and that is exactly the right
lesson about where capability actually comes from.

## Core concepts

### The configuration

```python
GPT_CONFIG_124M = {
    "vocab_size": 50257,     # BPE vocabulary
    "context_length": 1024,  # max sequence length
    "emb_dim": 768,          # d_model
    "n_heads": 12,           # attention heads (head_dim = 64)
    "n_layers": 12,          # transformer blocks
    "drop_rate": 0.1,
    "qkv_bias": False,
}
```

Learn these numbers. They recur constantly, and every larger GPT-2 variant scales the same dials.

### Layer normalization

Normalize across the **feature dimension within a single example** to mean 0, variance 1, then
apply learned `scale` and `shift`:

$$y = \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} \cdot \gamma + \beta$$

The learned parameters matter for the same reason as in
[G11](../../01-hands-on-ml-geron/notes/ch11.md): the network can undo the normalization if it
needs to, so nothing is lost.

**Why LayerNorm rather than BatchNorm:** it is independent of batch composition and batch size, so
it behaves identically at training and inference, works with variable-length sequences, and works
at batch size 1. That last property is what generation needs.

Implementation detail Raschka calls out: use **biased variance** (`unbiased=False`, dividing by
*n* rather than *n−1*) to match GPT-2's original TensorFlow implementation. This matters when you
load OpenAI's weights in chapter 5 — otherwise your outputs drift.

`[dated]` **RMSNorm**, which drops mean-centering and only rescales, is now common in newer models.
Cheaper, works as well.

### GELU

$$\text{GELU}(x) \approx 0.5x\left(1 + \tanh\left[\sqrt{2/\pi}\left(x + 0.044715x^3\right)\right]\right)$$

Smooth, and unlike ReLU it is **nonzero for small negative inputs**. Two consequences: no dead
neurons ([G11](../../01-hands-on-ml-geron/notes/ch11.md)), and a smoother optimization landscape.

Plot GELU against ReLU. The visual — a gentle dip below zero on the negative side rather than a
hard elbow — is worth having in your head.

`[dated]` **SwiGLU** has largely replaced GELU in newer models' FFNs.

### The feedforward network

```
Linear(768 → 3072) → GELU → Linear(3072 → 768)
```

The **4× expansion** is convention, and it is where the capacity lives: 768 × 3072 × 2 ≈ **4.7M
parameters per block**, versus ~2.4M for the attention. Across 12 blocks, the FFNs hold roughly
two-thirds of the model's non-embedding parameters.

Attention moves information *between* positions; the FFN processes each position independently
([A3](../../02-hands-on-llms-alammar/notes/ch03.md)). Evidence suggests the FFN acts as a
key-value memory storing factual associations.

### Shortcut connections — with the demonstration

Raschka does the single best thing in the chapter here: he builds a 5-layer network **with and
without** shortcut connections and prints the gradient magnitude at each layer.

Without shortcuts, gradients shrink by orders of magnitude as they flow back — the vanishing
gradient problem, made visible. With shortcuts, they stay comparable across layers.

**Run this experiment.** It converts an abstract concern into an observed fact, and it is the
justification for the entire architecture of the block.

### The transformer block

```python
# Pre-norm: normalize BEFORE the sublayer, add the result to the residual stream
shortcut = x
x = self.norm1(x)
x = self.att(x)
x = self.drop_shortcut(x)
x = x + shortcut          # residual connection

shortcut = x
x = self.norm2(x)
x = self.ff(x)
x = self.drop_shortcut(x)
x = x + shortcut
```

Two sublayers, each: normalize → transform → dropout → add back.

**Pre-norm vs post-norm.** The original 2017 paper normalized *after* the sublayer. GPT-2 and
everything since normalize *before*, because pre-norm trains far more stably at depth — the
residual path stays clean, so gradients flow unimpeded to the embeddings. Raschka uses pre-norm.

Crucially, **the block preserves its input shape**. `(batch, seq, 768)` in, `(batch, seq, 768)`
out. That is what lets you stack twelve of them with `nn.Sequential`.

### The full model

```
tokens
  → token embedding + positional embedding
  → dropout
  → 12 × TransformerBlock
  → final LayerNorm
  → Linear(768 → 50257)     [the LM head, no bias]
  → logits
```

**Parameter count.** Raschka's arithmetic gives 163M, but GPT-2 small is 124M. The difference is
**weight tying** — the output head shares weights with the token embedding matrix
(50257 × 768 = 38.6M). Same matrix, used to embed on the way in and to unembed on the way out.

That is not just a compression trick. It says the geometry of "which token is this" and "which
token comes next" is the same space, which is a genuinely elegant idea.

Raschka implements the untied version for clarity and explains the tying — do the arithmetic
yourself, it is a good check on whether you understand where the parameters live.

### Generating text

The generation loop, which is shorter than people expect:

```python
def generate_text_simple(model, idx, max_new_tokens, context_size):
    for _ in range(max_new_tokens):
        idx_cond = idx[:, -context_size:]        # crop to the context window
        with torch.no_grad():
            logits = model(idx_cond)
        logits = logits[:, -1, :]                 # ONLY the last position matters
        probas = torch.softmax(logits, dim=-1)
        idx_next = torch.argmax(probas, dim=-1, keepdim=True)   # greedy
        idx = torch.cat((idx, idx_next), dim=1)   # append and repeat
    return idx
```

Three things worth noticing:

1. **Only the last position's logits are used.** All positions are computed; only one predicts.
2. **The context is cropped**, since positions beyond `context_length` have no positional
   embedding.
3. **The softmax is redundant here** — argmax over logits gives the same answer. It matters in
   chapter 5 when sampling replaces argmax.

Run it. The output is gibberish. The architecture is correct and the weights are random —
capability is entirely in the weights, and chapter 5 is where they come from.

## Key code

```python
class GPTModel(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.tok_emb = nn.Embedding(cfg["vocab_size"], cfg["emb_dim"])
        self.pos_emb = nn.Embedding(cfg["context_length"], cfg["emb_dim"])
        self.drop_emb = nn.Dropout(cfg["drop_rate"])
        self.trf_blocks = nn.Sequential(
            *[TransformerBlock(cfg) for _ in range(cfg["n_layers"])]
        )
        self.final_norm = LayerNorm(cfg["emb_dim"])
        self.out_head = nn.Linear(cfg["emb_dim"], cfg["vocab_size"], bias=False)

    def forward(self, in_idx):
        _, seq_len = in_idx.shape
        x = self.tok_emb(in_idx) + self.pos_emb(
            torch.arange(seq_len, device=in_idx.device)
        )
        x = self.drop_emb(x)
        x = self.trf_blocks(x)      # shape-preserving, so stacking works
        return self.out_head(self.final_norm(x))
```

Yours: [`src/aieng/transformer/gpt.py`](../../../src/aieng/transformer/gpt.py).

## Gotchas

- **Unbiased variance in LayerNorm.** Use `unbiased=False` to match GPT-2, or loaded weights
  produce subtly wrong outputs.
- **Post-norm instead of pre-norm.** Trains much worse at depth. Normalize before the sublayer.
- **Forgetting the residual add.** The model will not train, and the failure looks mysterious.
- **`pos_emb` on the wrong device.** `torch.arange(seq_len, device=in_idx.device)`.
- **Not cropping to `context_length`** during generation. Index error out of the positional table.
- **Using all positions' logits to generate.** Only the last one predicts the next token.
- **Forgetting `model.eval()`.** Dropout stays active and generation degrades randomly.
- **Expecting coherent output from an untrained model.** It is random. That is the point.

## Flashcards

<!-- card -->
Q: Why does a transformer use LayerNorm rather than BatchNorm?
A: LayerNorm normalizes across features within one example, so it is independent of batch size and composition — identical behaviour at training and inference, works with variable-length sequences, and works at batch size 1 (which generation requires).
<!-- /card -->

<!-- card -->
Q: What is the structure of a transformer block?
A: Two sublayers, each wrapped in a pre-normalized residual: `x = x + dropout(attention(norm(x)))` then `x = x + dropout(ffn(norm(x)))`. The block preserves its input shape, which is what allows stacking.
<!-- /card -->

<!-- card -->
Q: Pre-norm vs post-norm — which and why?
A: Pre-norm (normalize before the sublayer) is used by GPT-2 and everything since, because it trains far more stably at depth: the residual path stays clean so gradients flow unimpeded. The original 2017 paper used post-norm.
<!-- /card -->

<!-- card -->
Q: Why does the feedforward network expand to 4× the model dimension?
A: Convention, and it is where the capacity lives — 768→3072→768 is about 4.7M parameters per block versus ~2.4M for attention. Across a model, FFNs hold roughly two-thirds of non-embedding parameters and appear to store factual associations.
<!-- /card -->

<!-- card -->
Q: What is weight tying, and how much does it save in GPT-2 small?
A: The output head shares its weight matrix with the token embedding table. That saves 50257 × 768 = 38.6M parameters — the difference between the naive 163M count and GPT-2 small's actual 124M. Conceptually it says "which token is this" and "which token comes next" share a geometry.
<!-- /card -->

<!-- card -->
Q: In the generation loop, why are only the last position's logits used?
A: Every position is computed in the forward pass, but only the final position predicts the *next* token. Earlier positions exist to be attended to.
<!-- /card -->

<!-- card -->
Q: Why must LayerNorm use biased variance (`unbiased=False`) in this implementation?
A: To match GPT-2's original TensorFlow implementation, which divides by n rather than n−1. Using the unbiased estimator makes loaded OpenAI weights produce subtly wrong outputs.
<!-- /card -->
