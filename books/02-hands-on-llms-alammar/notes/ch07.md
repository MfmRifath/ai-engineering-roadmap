# A7 — Advanced Text Generation Techniques and Tools

> **Thesis:** An LLM call is stateless and single-shot; everything that makes it feel otherwise —
> memory, multi-step reasoning, tool use — is scaffolding you build around it.

## Why this chapter matters

This is the chapter where the LLM stops being a function and starts being a **component in a
system**. Three ideas carry forward hard: chains, memory, and agents. All three get much fuller
treatment later — agents across all of [Lanham](../../05-ai-agents-in-action-lanham/), memory in
[L8](../../05-ai-agents-in-action-lanham/notes/ch08.md) — so read this as the orientation.

`[framework-specific]` The chapter uses LangChain heavily. LangChain's dominance has softened
considerably since publication; many teams now use provider SDKs directly plus small focused
libraries. **Learn the patterns, hold the framework loosely.** The patterns are permanent.

## Core concepts

### Model I/O and quantized loading

Loading a quantized model locally (GGUF via `llama.cpp`, or bitsandbytes 4-bit) is the practical
enabler for everything else in the book — it is what lets you iterate without an API bill.

The mechanism is [G19](../../01-hands-on-ml-geron/notes/ch19.md)'s post-training quantization:
store weights as 4- or 8-bit integers with a scale factor per group, dequantize on use. Memory
drops roughly 4–8×; quality drops a little.

Rough rule for VRAM: **parameters × bytes-per-parameter**, plus overhead. A 7B model at 4-bit ≈
3.5 GB of weights; add the KV cache ([A3](ch03.md)) and context, and 6 GB is a realistic minimum.
[H7](../../04-ai-engineering-huyen/notes/ch07.md) does this arithmetic properly.

### Chains

A **chain** pipes the output of one call into the input of the next. The simplest useful unit is
a prompt template plus a model plus an output parser.

Multi-prompt chains decompose a task: generate a title → generate an outline from the title →
generate a section from the outline. The benefits are real — each step is separately testable and
separately debuggable — and so are the costs: latency adds up, and **errors compound**. A 90%
success rate over four sequential steps is 66% end to end.

That compounding is the single most important fact about multi-step LLM systems, and it recurs
as the central caution in [Lanham](../../05-ai-agents-in-action-lanham/).

### Memory

LLM APIs are **stateless**. The model has no memory between calls; the illusion of conversation
comes entirely from you resending history.

| Strategy | How | Cost | Loses |
|---|---|---|---|
| **Conversation buffer** | Send the whole history | Grows without bound | Nothing, until it overflows |
| **Windowed buffer** | Send the last *k* turns | Bounded | Anything older than k |
| **Summary** | LLM-summarize older turns | Bounded, extra calls | Detail, subtly |
| **Vector/retrieval** | Embed turns, retrieve relevant ones | Bounded | Continuity |

Every option trades fidelity for context budget. There is no free choice — which is exactly why
[L8](../../05-ai-agents-in-action-lanham/notes/ch08.md) treats memory as a first-class design
problem rather than a setting.

Summary memory has a specific hazard worth naming: **summarization is lossy and compounding.**
Summarize a summary enough times and you get confident nonsense. Keep the raw history if you can
afford it.

### Agents — the first look

An agent adds a **loop** and **tools**:

```
while not done:
    think    → the model decides what to do next
    act      → call a tool
    observe  → feed the result back into context
```

**ReAct** (Reason + Act) interleaves reasoning traces with actions, which both improves decisions
and makes the trajectory legible for debugging.

The important framing: **the model does not "call" anything.** It emits text (or a structured
function-call object) that *your code* interprets and executes, then you put the result back in
the context. The LLM is the decision-maker; your harness is everything else. Holding that clearly
prevents a lot of confused thinking about what agents are.

`[dated]` Function calling / tool use is now a first-class API feature with typed schemas, rather
than the text-parsing hack that early ReAct implementations used. [MCP](https://modelcontextprotocol.io)
has since emerged as a standard for exposing tools to models. Same pattern, better plumbing.

## Key code

```python
# Loading a quantized model locally — the practical enabler for iteration
from llama_cpp import Llama
llm = Llama(model_path="./models/phi-3-mini-q4.gguf", n_ctx=4096, n_gpu_layers=-1)

# A chain, without any framework — this is all a "chain" is
def chain(topic):
    title = generate(f"Write a title about {topic}. Title only.")
    outline = generate(f"Write a 5-point outline for an article titled: {title}")
    return generate(f"Write the introduction for:\n{title}\n{outline}")

# Windowed memory, also without a framework
class WindowMemory:
    def __init__(self, k=6):
        self.k, self.turns = k, []
    def add(self, role, content):
        self.turns.append({"role": role, "content": content})
        self.turns = self.turns[-self.k:]     # bounded context, older turns dropped
    def messages(self, system):
        return [{"role": "system", "content": system}, *self.turns]
```

Writing these without a framework once is worth more than reading a framework's docs three times.

## Gotchas

- **Assuming the model remembers.** It does not. Every call is fresh; history is your job.
- **Unbounded conversation buffers.** They grow until they blow the context window, and cost
  grows with them since you resend everything each turn.
- **Compounding summarization.** Summaries of summaries drift into confident invention.
- **Ignoring error compounding in chains.** 0.9⁴ = 0.66. Measure end-to-end, not per step.
- **Believing the model executes tools.** It emits a request; your code executes. All validation
  and authorization is yours.
- **No timeout or iteration cap on an agent loop.** Runaway loops are the classic agent failure
  and the classic surprise invoice. Always cap iterations.
- **Framework lock-in.** Learn the pattern; the library will change.
- **Quantizing without measuring.** Evaluate the quantized model on your task.

## Exercises

**Understand**
1. Why is an LLM API stateless, and what does that imply for building chat?
2. Compare the four memory strategies on cost and fidelity.
3. Explain precisely what happens when a model "calls a tool."
4. If each step succeeds 92% of the time, what is the end-to-end success rate over five steps?

**Build**
1. Implement all four memory strategies **without a framework**, then run the same 20-turn
   conversation through each. Measure tokens used and whether facts from turn 2 survive to turn 20.
2. Build a 4-step chain and instrument each step. Measure per-step and end-to-end success.
3. Write a minimal ReAct loop from scratch — no framework — with two tools (a calculator and a
   search stub). Cap iterations at 5. This is your first agent, and doing it by hand makes all of
   [Lanham](../../05-ai-agents-in-action-lanham/) easier.
4. Load the same model at fp16, 8-bit, and 4-bit. Measure VRAM, tokens/sec, and quality on 20
   prompts. Build the table.

## Flashcards

<!-- card -->
Q: Why does a chatbot need memory management at all?
A: LLM APIs are stateless — the model retains nothing between calls. The illusion of conversation exists only because you resend the history each turn, which costs tokens and eventually overflows the context window.
<!-- /card -->

<!-- card -->
Q: Compare the four conversation memory strategies.
A: Full buffer (perfect fidelity, unbounded cost); windowed buffer (bounded, loses anything older than k turns); summary (bounded, lossy and compounding); vector retrieval (bounded, retrieves relevant history but loses continuity).
<!-- /card -->

<!-- card -->
Q: What actually happens when an LLM "calls a tool"?
A: It emits text or a structured function-call object describing the desired call. *Your code* parses it, validates it, executes it, and inserts the result back into the context. The model is the decision-maker; the harness does everything else — including all authorization.
<!-- /card -->

<!-- card -->
Q: Why does error compounding matter in multi-step LLM systems?
A: Success rates multiply. Four steps at 90% each give 66% end to end; ten steps at 95% give 60%. This is the central constraint on agent reliability and the reason to measure end-to-end rather than per-step.
<!-- /card -->

<!-- card -->
Q: What is the ReAct pattern?
A: A loop that interleaves reasoning traces with actions: think about what to do, act by calling a tool, observe the result, repeat. The explicit reasoning both improves decisions and makes the trajectory debuggable.
<!-- /card -->
