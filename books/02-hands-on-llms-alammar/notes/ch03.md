# A3 — Looking Inside Large Language Models

> **Thesis:** A decoder-only transformer is a stack of identical blocks, each of which does two
> things — move information between positions (attention), then process each position
> independently (feedforward) — repeated until the last position's vector can predict the next
> token.

## Why this chapter matters

**The single most important chapter in the book.** Everything in Phase 5 assumes you can picture
this. Alammar's diagrams here are the reason the book exists, and if you can draw the forward pass
from memory afterwards, [Raschka](../../03-build-llm-from-scratch-raschka/) becomes transcription
of something you already understand.

Read it three times: once fast, once with a pen, once asking only about the KV cache.

## Core concepts

### The forward pass, end to end

```
token IDs
   │
   ├─► embedding lookup            (vocab, d_model) → one vector per token
   ├─► + positional information    (learned, sinusoidal, or RoPE)
   │
   ├─► ┌─ Transformer block ──────────────────┐   ×N
   │   │  x = x + attention(layer_norm(x))    │   ← moves info BETWEEN positions
   │   │  x = x + ffn(layer_norm(x))          │   ← processes EACH position alone
   │   └────────────────────────────────────── ┘
   │
   ├─► final layer norm
   ├─► language model head          (d_model, vocab) → logits
   └─► softmax + sampling          → one token
```

Two facts that make everything clearer:

1. **Only the last position matters for the next token.** All positions are computed, but
   generation reads the final position's logits. The others exist to be attended to.
2. **The block does exactly two jobs.** Attention is the *only* place information moves between
   positions. The feedforward network processes each position in isolation. That division is
   worth burning in.

### The residual stream

The `x = x + ...` pattern is not incidental. Think of `x` as a **residual stream** running the
length of the network, into which each block *writes* an update. Every layer reads from the
stream and adds to it.

This framing — from [G14](../../01-hands-on-ml-geron/notes/ch14.md)'s ResNet — is how
interpretability research talks about transformers, and it makes several things intuitive:

- Layers communicate through a shared bus, not just sequentially.
- An untrained block adds ~nothing, so depth is safe.
- Gradients have a direct highway back to the embeddings.

### Attention, revisited concretely

For each position, three projections of its vector:

- **Query** — what am I looking for?
- **Key** — what do I offer?
- **Value** — what do I contribute if chosen?

$$\text{Attention}(Q,K,V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}} + M\right)V$$

**Causal masking** *M* sets attention to future positions to −∞ before the softmax, so they get
weight 0. This is what makes the model *causal* — position *i* can attend to positions ≤ *i* only.
Without it, the model would see the answer while predicting it, and training would be trivially
degenerate.

**Multi-head:** run *h* attentions in parallel in lower-dimensional subspaces, concatenate,
project. Different heads learn different relationships. Alammar's visualizations of heads tracking
syntax vs coreference are worth studying.

### Parallel processing and context size

During **training**, all positions are computed simultaneously — one big matrix multiply. This is
the transformer's decisive advantage over RNNs
([G15](../../01-hands-on-ml-geron/notes/ch15.md)).

But attention is **quadratic in sequence length**: the score matrix is *n × n*. Double the context
and you quadruple attention compute and memory. That single fact drives all of
[H9](../../04-ai-engineering-huyen/notes/ch09.md) and every "efficient attention" paper.

### The KV cache — the most practically important idea here

During **generation**, the naive approach recomputes everything for each new token: generate token
*n+1*, then re-run the whole prefix to generate *n+2*. That is enormously wasteful, because the
keys and values for earlier positions **do not change** — they depend only on tokens already
fixed.

So cache them. For each new token you compute only *its* Q, K, V, append K and V to the cache, and
attend over the cached history.

This is why:

- **Time-to-first-token (prefill) and time-per-output-token (decode) are different metrics.**
  Prefill processes the whole prompt in parallel and is compute-bound; decode generates one token
  at a time and is memory-bandwidth-bound.
- **KV cache memory grows linearly with context length and batch size**, and for long contexts it
  can exceed the model weights. It is the binding constraint on how many concurrent requests you
  can serve.
- **Prompt caching** (offered by several APIs) is literally reusing a KV cache across requests
  with a shared prefix — which is why putting the stable part of your prompt first is a real
  optimization.

### Inside the block

**Layer normalization** ([G11](../../01-hands-on-ml-geron/notes/ch11.md)) — normalizes across
features within one example, so batch composition is irrelevant.

`[dated]` Two shifts since: **pre-norm** (normalize *before* the sublayer, as shown above) has
replaced the original post-norm because it trains far more stably at depth. And **RMSNorm** — which
drops the mean-centering and only rescales — is now common; it is cheaper and works as well.

**The feedforward network** is two linear layers with a nonlinearity, typically expanding to 4×
`d_model` and back. It holds **roughly two-thirds of the model's parameters**. Evidence suggests
it functions as a key-value memory storing factual associations — which is why most knowledge
editing research targets it.

`[dated]` **SwiGLU** has largely replaced plain GELU in the FFN of modern models.

### Recent architectural improvements

The chapter's coverage of what changed after the original paper:

**Efficient attention.**

| Variant | Idea | Effect |
|---|---|---|
| **MQA** (multi-query) | All heads share one K/V head | Much smaller KV cache, some quality loss |
| **GQA** (grouped-query) | Head *groups* share K/V | The current standard — most of the saving, little loss |
| **FlashAttention** | IO-aware tiling; never materialize the n×n matrix | Same math, much faster, far less memory |
| **Sliding window** | Attend only to the last *w* tokens | Linear rather than quadratic |

FlashAttention is worth understanding as a *category*: it changes no mathematics at all. It is
purely about memory hierarchy — keeping tiles in fast SRAM rather than round-tripping the huge
attention matrix to HBM. A great many "efficiency" wins in this field are of this kind.

**Rotary positional embeddings (RoPE).** Rather than adding a position vector at the input, rotate
Q and K by an angle proportional to position. The dot product between two rotated vectors then
depends on their **relative** distance — which is what actually matters for language, and which
extrapolates better to longer contexts than absolute encodings.

**Mixture of Experts (MoE).** Replace the FFN with many expert FFNs and a router that activates
only a few per token. Large *total* parameters, small *active* parameters — more capacity for the
same inference cost.

## Key code

```python
import torch, math

def causal_self_attention(x, W_q, W_k, W_v, n_heads):
    B, T, C = x.shape
    q = (x @ W_q).view(B, T, n_heads, C // n_heads).transpose(1, 2)
    k = (x @ W_k).view(B, T, n_heads, C // n_heads).transpose(1, 2)
    v = (x @ W_v).view(B, T, n_heads, C // n_heads).transpose(1, 2)

    scores = q @ k.transpose(-2, -1) / math.sqrt(q.size(-1))
    mask = torch.triu(torch.ones(T, T, dtype=torch.bool), diagonal=1)
    scores = scores.masked_fill(mask, float("-inf"))     # causal: no peeking ahead

    out = torch.softmax(scores, dim=-1) @ v
    return out.transpose(1, 2).contiguous().view(B, T, C)


# Seeing the KV cache pay off
from transformers import AutoModelForCausalLM
model = AutoModelForCausalLM.from_pretrained("gpt2")
out = model(input_ids, use_cache=True)
past = out.past_key_values          # per layer: (key, value) for every prior position
# Next step: feed ONE token plus `past`, instead of the whole sequence again.
```

Full implementation: [`src/aieng/transformer/attention.py`](../../../src/aieng/transformer/attention.py).

## Gotchas

- **Omitting the causal mask.** Training looks fantastic and generation is garbage — the model
  learned to read the answer.
- **Masking after the softmax.** The mask must be applied to the *scores*, before softmax, using
  −∞. Zeroing probabilities afterwards leaves them unnormalized.
- **Forgetting `use_cache=False` during training.** Training processes all positions at once;
  the cache is a generation-time optimization only.
- **Underestimating KV cache memory.** For long contexts and large batches it can exceed the
  weights. It is usually what actually limits your concurrency.
- **Assuming quadratic attention doesn't matter at your scale.** 8k context is 64× the attention
  cost of 1k.
- **Confusing `d_model` with `d_head`.** `d_head = d_model / n_heads`. The √d_k scaling uses
  `d_head`.
- **Putting the variable part of a prompt first.** It defeats prefix KV caching. Stable content
  first, variable content last.

## Flashcards

<!-- card -->
Q: What are the two operations in a transformer block, and how do they differ?
A: Attention moves information *between* positions; the feedforward network processes *each position independently*. Attention is the only place cross-position information flows. Both are wrapped in residual connections around a layer norm.
<!-- /card -->

<!-- card -->
Q: What is the residual stream?
A: The `x` carried through `x = x + attention(norm(x))` and `x = x + ffn(norm(x))` — a shared bus running the depth of the network that each block reads from and writes an update into. It also gives gradients a direct path to the embeddings.
<!-- /card -->

<!-- card -->
Q: What is the KV cache and why is it valid?
A: During generation, the keys and values for earlier positions depend only on tokens already fixed, so they never change. Caching them means each new token computes only its own Q/K/V and attends over cached history, instead of re-running the whole prefix.
<!-- /card -->

<!-- card -->
Q: Why are prefill and decode bounded by different resources?
A: Prefill processes the entire prompt in parallel — lots of arithmetic on lots of data, so it is compute-bound. Decode produces one token at a time, reading the whole model and KV cache per token, so it is memory-bandwidth-bound.
<!-- /card -->

<!-- card -->
Q: Why is attention quadratic, and why does it matter?
A: The score matrix is n × n for a sequence of n tokens, so compute and memory scale with n². Doubling context quadruples the cost — the reason FlashAttention, GQA, and sliding-window attention exist.
<!-- /card -->

<!-- card -->
Q: What does FlashAttention change?
A: None of the mathematics — the output is identical. It is an IO-aware tiled implementation that never materializes the full n×n matrix in slow HBM, keeping tiles in fast SRAM instead. A pure memory-hierarchy win.
<!-- /card -->

<!-- card -->
Q: What is GQA and what does it trade?
A: Grouped-query attention: groups of query heads share a single key/value head. It shrinks the KV cache substantially (the main serving bottleneck) for a small quality cost, and is the current standard — between full MHA and the more aggressive MQA.
<!-- /card -->

<!-- card -->
Q: What does RoPE do differently from additive positional encodings?
A: It rotates the query and key vectors by an angle proportional to position, so their dot product depends on *relative* distance rather than absolute position. This matches what language actually needs and extrapolates better to longer contexts.
<!-- /card -->

<!-- card -->
Q: Roughly where do a transformer's parameters live?
A: About two-thirds in the feedforward networks, the rest in attention projections and embeddings. Evidence suggests the FFN acts as a key-value memory for factual associations, which is why knowledge-editing research targets it.
<!-- /card -->
