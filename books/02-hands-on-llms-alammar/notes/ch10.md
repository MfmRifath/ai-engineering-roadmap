# A10 — Creating Text Embedding Models

> **Thesis:** An embedding model is defined by what you told it should be *similar* — so training
> one is mostly the work of constructing pairs, and the negatives matter more than the positives.

## Why this chapter matters

Everything retrieval-shaped rests on embeddings: RAG ([A8](ch08.md)), clustering
([A5](ch05.md)), classification ([A4](ch04.md)), agent memory
([L8](../../05-ai-agents-in-action-lanham/notes/ch08.md)). When an off-the-shelf model
underperforms on your domain — jargon-heavy, non-English, or a peculiar notion of relevance —
this chapter is how you fix it.

It is also the clearest statement of the contrastive recipe you have now met three times.

## Core concepts

### Why a generative LLM's vectors are poor embeddings

A decoder-only LLM is optimized for next-token prediction. Nothing in that objective asks for
"the mean of these vectors should be close to the mean of a paraphrase's vectors." Cosine
similarity over mean-pooled GPT vectors is measuring something the model was never trained to
make meaningful.

**Embedding models are trained specifically so that cosine similarity means what you want.**
That is the whole distinction.

### Sentence-BERT and the pooling problem

BERT gives a vector per token. To get one vector per sentence you pool — and naive pooling of a
vanilla BERT is famously poor at semantic similarity.

**SBERT** fixes it with a **siamese** setup: the same encoder embeds both sentences of a pair,
mean-pools, and is trained so the resulting vectors are close for similar sentences. The
architecture barely changes; the *objective* changes completely.

### Contrastive learning, stated properly

You need triples, or something that yields them:

- **Anchor** — the query
- **Positive** — something that should be close
- **Negative** — something that should be far

**Where positives come from** — and this is the practical crux:

| Source | Example |
|---|---|
| Natural pairs | (question, accepted answer), (title, abstract), (query, clicked doc) |
| Labeled NLI | Entailment pairs are positives, contradictions are negatives |
| **Augmentation** | Two dropout-masked views of the *same* sentence (TSDAE, SimCSE) |
| Synthetic | LLM-generated queries for your documents |

That third row is remarkable: **you can train a usable embedding model with no labeled data at
all.** SimCSE's insight is that passing one sentence through the encoder twice with different
dropout masks gives two slightly different vectors — a positive pair created out of nothing.

### The losses

| Loss | Needs | Notes |
|---|---|---|
| **Softmax/classification** | Labeled pairs | The original SBERT NLI approach |
| **Cosine similarity** | Pairs with similarity scores | Regression toward a target score |
| **Triplet** | (anchor, positive, negative) | Margin loss — see below |
| **MultipleNegativesRankingLoss (MNRL)** | (anchor, positive) only | **The default. Use this.** |

**MNRL** is the one to know. Given a batch of (anchor, positive) pairs, it treats every *other*
positive in the batch as a negative for the current anchor, and applies cross-entropy over the
similarities. So:

- You only need positive pairs — no negative mining required to get started.
- **Larger batches give more negatives and better results.** Batch size is a quality
  hyperparameter here, not just a memory one. This is the same dynamic as CLIP
  ([A9](ch09.md)).

**Triplet loss** carries the margin idea from SVMs
([G5](../../01-hands-on-ml-geron/notes/ch05.md)): push the positive closer than the negative *by
at least a margin*. Once the margin is satisfied, that triple contributes no gradient — which is
exactly why hard negatives matter.

### Hard negatives — the highest-leverage detail

**Random negatives are too easy.** For the query "how do I reset my password", a random negative
about cooking is trivially distinguished; the model learns nothing from it. After a while, most
random triples produce near-zero gradient.

**Hard negatives** are plausible but wrong — a document about resetting your *username*. These
are where the model actually learns the decision boundary.

Mine them by retrieving with the current model and taking high-ranked non-relevant results.

**But beware false negatives.** Mine too aggressively and you will pick up documents that are
actually relevant but unlabeled, and you will train the model to push away correct answers.
Standard mitigations: skip the very top ranks, or use a cross-encoder to filter mined negatives.

### Evaluation

MTEB (Massive Text Embedding Benchmark) is the standard leaderboard. Useful for shortlisting,
misleading as a decision: **benchmark rank does not predict performance on your data.** Build a
small evaluation set from your own domain — 50 hand-labeled (query, relevant doc) pairs is enough
to be decisive — and measure recall@k on that.

Practical selection criteria beyond quality: dimension (storage and search cost), sequence length
limit (long documents get truncated *silently*), language coverage, and license.

`[dated]` **Matryoshka embeddings**, trained so that truncating the vector to fewer dimensions
still works, let you trade storage for quality after the fact. Widely supported now, and a good
default when you have them.

## Key code

```python
from sentence_transformers import SentenceTransformer, InputExample, losses
from torch.utils.data import DataLoader

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

# MNRL needs only positive pairs — every other positive in the batch is a negative
train = [InputExample(texts=[q, positive_doc]) for q, positive_doc in pairs]
loader = DataLoader(train, shuffle=True, batch_size=64)   # bigger batch = more negatives
loss = losses.MultipleNegativesRankingLoss(model)

model.fit(train_objectives=[(loader, loss)],
          epochs=1, warmup_steps=100,
          show_progress_bar=True)

# Hard negative mining: retrieve with the current model, take plausible-but-wrong hits.
# Skip the top few ranks — those are often unlabeled true positives.
hits = model.similarity(query_emb, doc_emb).topk(20).indices
hard_negs = [d for d in hits[3:] if d not in known_positives]
```

## Gotchas

- **Random negatives only.** The model plateaus early because most triples give no gradient. Mine
  hard negatives.
- **Over-aggressive negative mining.** You will mine false negatives — real answers that happen to
  be unlabeled — and teach the model to reject correct results.
- **Small batches with MNRL.** Batch size directly controls how many negatives each anchor sees.
  It is a quality knob.
- **Ignoring `max_seq_length`.** Documents longer than the limit are truncated **silently**. Check
  it, always.
- **Asymmetric models without prefixes.** Same trap as [A8](ch08.md).
- **Choosing by MTEB rank alone.** Build a domain eval set. It takes an hour and it decides better.
- **Fine-tuning before establishing a baseline.** Measure the off-the-shelf model on your eval set
  first, or you will not know whether the fine-tune helped.
- **Re-embedding drift.** Changing the model means reindexing the entire corpus. Plan for it.

## Exercises

**Understand**
1. Why are a generative LLM's hidden states poor sentence embeddings?
2. How does MNRL manufacture negatives, and why does batch size affect quality?
3. What is a hard negative, and what is the risk of mining them aggressively?
4. How can SimCSE create positive pairs from unlabeled text?

**Build**
1. Build a 50-pair domain evaluation set for a corpus you care about. Measure three off-the-shelf
   embedding models on recall@5. **Do this before any fine-tuning.**
2. Fine-tune with MNRL on domain pairs and measure the improvement against that baseline.
3. Compare random negatives against mined hard negatives, everything else held constant. The gap
   is the lesson.
4. Implement SimCSE-style unsupervised training — same sentence, two dropout masks — on unlabeled
   text from your domain. See how far you get with zero labels.
5. Sweep batch size over [8, 32, 128] with MNRL and plot the effect on retrieval quality.
