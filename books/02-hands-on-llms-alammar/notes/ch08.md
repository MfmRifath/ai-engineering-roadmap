# A8 — Semantic Search and Retrieval-Augmented Generation

> **Thesis:** RAG is search plus a prompt — which means every RAG failure is either a search
> failure or a prompt failure, and the search failures are the ones nobody measures.

## Why this chapter matters

RAG is the most common LLM architecture in production, and this chapter gives you the working
version. [H6](../../04-ai-engineering-huyen/notes/ch06.md) then gives you the *production*
version, which is largely a catalogue of the ways this one breaks. Build this first — you need
the naive system before the critique is meaningful.

Project [p2](../../../projects/p2-rag-over-my-library/) is this chapter applied to the PDFs in
your own `library/`.

## Core concepts

### Three kinds of search

| Type | Matches on | Strong at | Weak at |
|---|---|---|---|
| **Keyword** (BM25) | Exact terms | Names, IDs, codes, rare terms | Synonyms, paraphrase |
| **Dense/semantic** | Embedding similarity | Meaning, paraphrase | Exact strings, rare tokens |
| **Hybrid** | Both, fused | Most things | Complexity |

**Dense retrieval does not subsume keyword retrieval.** This is the correction most people need.
Search for error code `E-4471` and a dense retriever will happily return semantically similar
error discussions that do not contain it. BM25 nails it instantly.

**Hybrid is the right default in production.** Run both, fuse the rankings — Reciprocal Rank
Fusion is the standard, simple, parameter-light method.

### The dense retrieval pipeline

```
documents → chunk → embed → index
query → embed → search → [rerank] → top-k
```

**Chunking** is where most RAG quality is won or lost, and it is under-discussed:

- Too small → context is fragmented; a chunk lacks the information needed to answer.
- Too large → the embedding averages over multiple topics and matches nothing well.
- **Overlap** (10–20%) prevents an answer from being split across a boundary.
- **Respect structure.** Split on paragraphs, sections, or headings, not blind character counts.
  A chunk that starts mid-sentence embeds poorly.

Rules of thumb: 200–500 tokens with 10–20% overlap for prose. But *measure it* — chunking is a
hyperparameter and it interacts with your document type.

**Embedding.** Use a model trained for retrieval ([A10](ch10.md)), not a generative model's
hidden states. Note that many retrieval models are **asymmetric** — they expect a prefix like
`"query: "` on queries and `"passage: "` on documents. Skipping this quietly degrades results,
and it is a very common bug.

**Indexing.** Exact search is fine up to ~100k vectors. Beyond that, approximate nearest neighbour
(HNSW, IVF) trades a little recall for a lot of speed.

### Reranking — the highest-value addition

A **cross-encoder** takes the query and a document *together* and scores their relevance jointly.

This is the crucial architectural distinction:

- A **bi-encoder** (your embedding model) encodes query and document *separately*. Fast — you
  precompute document vectors — but the two never interact until a dot product at the end.
- A **cross-encoder** encodes them *together*, so attention runs across both. Much more accurate,
  and far too slow to run over a whole corpus.

So: retrieve 50–100 candidates with the fast bi-encoder, rerank them with the slow cross-encoder,
keep the top 3–5. **This two-stage pattern is the single highest-leverage improvement to a naive
RAG system**, and it is frequently skipped.

### RAG

Retrieve, stuff into the prompt, generate with instructions to answer *from the provided
context*.

```
Answer the question using only the context below.
If the context does not contain the answer, say so.

### Context
{retrieved_chunks}

### Question
{query}
```

Two things this buys: current and private knowledge without retraining, and **citations** — you
know which chunks were used, so the answer is auditable. Citation is a large part of why RAG
beats fine-tuning for factual tasks.

**The failure modes**, which [H6](../../04-ai-engineering-huyen/notes/ch06.md) expands:

- **Retrieval miss** — the answer was never retrieved. The generator cannot fix this, and this is
  the majority of RAG failures.
- **Distraction** — irrelevant chunks degrade the answer. More context is not better.
- **Lost in the middle** — models attend less reliably to the middle of a long context. Put the
  most relevant chunks at the edges.
- **Ignoring the context** — the model answers from parametric knowledge instead. Instruct it
  explicitly, and evaluate for it.
- **Conflicting sources** — two chunks disagree and the model picks arbitrarily.

**The measurement point:** evaluate retrieval and generation *separately*. Retrieval has ground
truth — did the right chunk come back? — so it is measurable with the metrics from
[G3](../../01-hands-on-ml-geron/notes/ch03.md): recall@k, precision@k, MRR, nDCG. Generation is
harder ([H3](../../04-ai-engineering-huyen/notes/ch03.md)). If you measure only end-to-end
quality you will never know which half to fix.

## Key code

```python
from sentence_transformers import SentenceTransformer, CrossEncoder
import numpy as np

# Stage 1 — fast bi-encoder retrieval over the whole corpus
bi = SentenceTransformer("BAAI/bge-base-en-v1.5")
doc_emb = bi.encode(chunks, normalize_embeddings=True)          # precomputed once
q_emb = bi.encode(["query: " + query], normalize_embeddings=True)  # note the prefix!
candidates = np.argsort(-(doc_emb @ q_emb.T).ravel())[:50]

# Stage 2 — slow cross-encoder reranking over just those 50
ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
scores = ce.predict([(query, chunks[i]) for i in candidates])
top = [chunks[i] for i in np.array(candidates)[np.argsort(-scores)[:5]]]

# Stage 3 — generate, grounded, with an explicit escape hatch
prompt = f"""Answer using only the context. If it isn't there, say you don't know.

### Context
{chr(10).join(f"[{i}] {c}" for i, c in enumerate(top))}

### Question
{query}"""
```

## Gotchas

- **Skipping keyword search entirely.** Dense retrieval fails on exact identifiers. Go hybrid.
- **Missing the query/passage prefix.** Asymmetric models need it. Silent quality loss.
- **Chunking by character count without respecting structure.** Chunks starting mid-sentence
  embed badly.
- **No overlap.** Answers split across a boundary become unretrievable.
- **No reranker.** The cheapest big win in RAG, routinely skipped.
- **Stuffing 20 chunks in.** Distraction and lost-in-the-middle. Fewer, better chunks win.
- **Not evaluating retrieval separately.** You cannot fix what you cannot localize.
- **Re-embedding with a different model than you indexed with.** Silent garbage.
- **Forgetting to normalize embeddings** before using dot product as cosine similarity.
- **No "I don't know" escape hatch.** Without it the model will confabulate from an empty
  retrieval.

## Flashcards

<!-- card -->
Q: Why doesn't dense retrieval replace keyword search?
A: Dense retrieval matches meaning, so it fails on exact strings — error codes, IDs, rare product names, specific numbers. BM25 finds those instantly. Hybrid retrieval with rank fusion is the production default.
<!-- /card -->

<!-- card -->
Q: Bi-encoder vs cross-encoder?
A: A bi-encoder embeds query and document separately, so document vectors are precomputable and search is fast — but the two never interact until a final dot product. A cross-encoder processes them together with full attention across both: far more accurate, far too slow for a whole corpus.
<!-- /card -->

<!-- card -->
Q: What is the two-stage retrieval pattern and why is it high-leverage?
A: Retrieve 50–100 candidates with the fast bi-encoder, then rerank them with a slow cross-encoder and keep the top 3–5. It gets cross-encoder accuracy at bi-encoder cost, and it is the cheapest large improvement to a naive RAG system.
<!-- /card -->

<!-- card -->
Q: Why does chunk overlap matter?
A: Without it, an answer spanning a chunk boundary is split so that neither chunk contains it completely — making it effectively unretrievable. 10–20% overlap is typical.
<!-- /card -->

<!-- card -->
Q: Name five RAG failure modes.
A: Retrieval miss (the answer was never retrieved — the most common); distraction from irrelevant chunks; lost-in-the-middle positional weakness; the model ignoring context in favor of parametric knowledge; and conflicting retrieved sources.
<!-- /card -->

<!-- card -->
Q: Why evaluate retrieval and generation separately?
A: Retrieval has ground truth — did the right chunk come back? — and is measurable with recall@k, precision@k, MRR, nDCG. Generation quality is much harder to measure. End-to-end scores alone never tell you which half to fix.
<!-- /card -->

<!-- card -->
Q: What is the query/passage prefix trap?
A: Many retrieval models are asymmetric and are trained expecting `"query: "` on queries and `"passage: "` on documents. Omitting the prefixes degrades results substantially, and it fails silently.
<!-- /card -->
