# A1 — An Introduction to Large Language Models

> **Thesis:** The history of language AI is a single long march toward better *representations* —
> from counting words, to dense vectors, to context-aware vectors — and the transformer is where
> that march arrived.

## Why this chapter matters

It picks up exactly where [G16](../../01-hands-on-ml-geron/notes/ch16.md) stops. Géron ends at
BERT and GPT-1; this chapter starts there and explains what happened next. It also gives you the
taxonomy — encoder-only vs decoder-only, proprietary vs open — that you need before any of the
practical chapters make sense.

## Core concepts

### The march of representations

| Era | Representation | What it captures | What it misses |
|---|---|---|---|
| 1950s–2000s | **Bag-of-words** | Word counts | Order, meaning, similarity |
| 2013 | **word2vec** | Dense static vectors | Context — one vector per word |
| 2017 | **Transformer** | Contextual vectors | (still: grounding, truth) |
| 2018 | **BERT / GPT** | Pretrained contextual | — |
| 2020+ | **Scaled LLMs** | Emergent capabilities | — |

**Bag-of-words** discards order entirely. "The dog bit the man" and "The man bit the dog" are
identical. It has no notion that "cat" and "kitten" are related — every word is orthogonal, which
is the one-hot problem from [G13](../../01-hands-on-ml-geron/notes/ch13.md).

**word2vec** (2013) fixed similarity with dense vectors trained by a contrastive objective: words
in similar contexts get similar vectors. The famous arithmetic — king − man + woman ≈ queen —
demonstrated that geometric structure encoded semantics. Its limitation is fatal though:
**one vector per word, regardless of context.** "Bank" has a single vector serving both the
riverbank and the financial institution.

**Contextual embeddings** solve that. In a transformer, the vector for a token depends on the
tokens around it, so "bank" gets different representations in different sentences. This is *the*
change, and it is what "attention" produces.

### The three architectural families

| | Encoder-only | Decoder-only | Encoder–decoder |
|---|---|---|---|
| Example | BERT | GPT, Llama, Claude | T5, original transformer |
| Attention | Bidirectional | **Causal** (past only) | Both |
| Trained by | Masked language modeling | Next-token prediction | Span corruption / seq2seq |
| Good at | Classification, NER, retrieval | **Generation** | Translation, summarization |
| Called | Representation models | Generative models | — |

The distinction is worth holding firmly because it determines what a model can *do*. BERT cannot
generate text — it sees the whole sequence at once and has no notion of "next." GPT can classify,
but usually less efficiently than a fine-tuned encoder.

`[dated]` Practice has consolidated hard on **decoder-only**. Encoders survive mainly as
**embedding models** for retrieval ([A10](ch10.md)) and as cheap classifiers ([A4](ch04.md)) —
which is not a small role, since every RAG system runs one.

### The training paradigm

Two stages, and the split is the reason any of this works:

1. **Pretraining** — self-supervised next-token (or masked-token) prediction on an enormous
   corpus. Expensive, done once, by very few organizations. Produces a **base model** that
   completes text but does not follow instructions.
2. **Fine-tuning / post-training** — supervised instruction tuning, then preference tuning
   (RLHF/DPO). Comparatively cheap. Produces an **instruct** or **chat** model.

The base/instruct distinction trips people up constantly. A base model given "Write a poem about
rain" may respond with more instructions, because that is a plausible continuation of the text.
It is not broken; it was never taught that the text is a request.
[R7](../../03-build-llm-from-scratch-raschka/notes/ch07.md) has you perform that teaching.

### Why LLMs are useful

The honest answer is **generality**. One model handles classification, extraction, summarization,
translation, and generation with no task-specific training — because the tasks were all expressible
as text continuation. That is what made the interface collapse from "train a model per task" to
"write a prompt."

### Responsible development

The chapter's treatment is short but the concerns are real and worth naming early: bias inherited
from training data, hallucination as a structural property (the model samples plausible tokens; it
has no truth predicate), the environmental cost of pretraining, IP questions around training data,
and misuse. [H5](../../04-ai-engineering-huyen/notes/ch05.md) and
[H10](../../04-ai-engineering-huyen/notes/ch10.md) turn these into engineering practice.

### Proprietary vs open models

| | Proprietary API | Open weights |
|---|---|---|
| Quality | Usually the frontier | Close and closing |
| Cost | Per token | Hardware + ops |
| Latency | Network hop | Local, controllable |
| Privacy | Data leaves your infrastructure | Stays put |
| Control | Version changes under you | Pinned forever |
| Fine-tuning | Limited | Full |

Not a moral question, an engineering one. Huyen's build-vs-buy framing in
[H4](../../04-ai-engineering-huyen/notes/ch04.md) is the systematic version.

**"Limited resources are all you need"** is a genuinely encouraging section: quantized open models
run on a laptop, and most of this book's code runs on free Colab. You do not need a cluster to
learn this.

### The stack

`[dated]` The book's ecosystem — `transformers`, `sentence-transformers`, LangChain, `llama.cpp`,
Ollama — is still broadly current, though LangChain's dominance has softened and direct API use
plus small purpose-built libraries is now common. Learn `transformers` properly; it is the durable
one.

## Key code

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, pipeline

model_id = "microsoft/Phi-3-mini-4k-instruct"
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, device_map="cuda",
                                             torch_dtype="auto")

generator = pipeline("text-generation", model=model, tokenizer=tokenizer,
                     return_full_text=False, max_new_tokens=200, do_sample=False)

# Chat templates matter: instruct models were trained with specific role markers.
# Passing a raw string instead of messages often degrades quality badly.
messages = [{"role": "user", "content": "Explain attention in two sentences."}]
print(generator(messages)[0]["generated_text"])
```

## Gotchas

- **Using a base model and expecting instruction following.** Check the model card. Base models
  complete; instruct models obey.
- **Skipping the chat template.** Instruct models are trained with specific role/turn markers.
  `tokenizer.apply_chat_template()` exists for this — hand-formatting the prompt silently costs
  quality.
- **Expecting an encoder model to generate.** BERT has no next-token head. Different tool.
- **Confusing model size with capability.** A well-post-trained 8B model routinely beats a poorly
  tuned 70B one on practical tasks.
- **Assuming word2vec-style static embeddings from an LLM.** LLM token embeddings are contextual;
  the same word yields different vectors in different sentences. That is the point.

## Exercises

**Understand**
1. Why can't bag-of-words distinguish "dog bites man" from "man bites dog," and why doesn't
   word2vec fix it?
2. What exactly does word2vec fail at that contextual embeddings solve?
3. Encoder-only vs decoder-only: what can each do, and why?
4. What is the difference between a base model and an instruct model?

**Build**
1. Load a small instruct model locally (Phi-3, Qwen, or Llama 3.2 1B) and generate text. Get this
   working before Phase 5 — you want a local model you can poke at.
2. Run the same prompt through a base model and its instruct sibling. Record both outputs. The
   difference is the entire post-training stage.
3. Compare `apply_chat_template` output with a hand-written prompt string for the same message.
   Look at the actual token IDs.
4. Install Ollama or `llama.cpp` and run a 4-bit quantized model on CPU. Note the tokens/sec —
   you will revisit that number in [H9](../../04-ai-engineering-huyen/notes/ch09.md).

## Flashcards

<!-- card -->
Q: What is word2vec's fundamental limitation?
A: One static vector per word regardless of context — "bank" gets a single embedding serving both the riverbank and the financial institution. Contextual embeddings from transformers give each occurrence its own vector.
<!-- /card -->

<!-- card -->
Q: Encoder-only vs decoder-only models — what determines what each can do?
A: Encoder-only (BERT) uses bidirectional attention and is trained by masked language modeling — great for classification and retrieval, incapable of generation. Decoder-only (GPT) uses causal attention and next-token prediction — built for generation.
<!-- /card -->

<!-- card -->
Q: What is the difference between a base model and an instruct model?
A: A base model is pretrained only and continues text; asked to "write a poem," it may produce more instructions because that is a plausible continuation. An instruct model has been post-trained (SFT + preference tuning) to treat the text as a request.
<!-- /card -->

<!-- card -->
Q: Why does skipping the chat template hurt quality?
A: Instruct models are fine-tuned with specific role and turn markers. Feeding a raw string puts the model off-distribution from its training format. Use `tokenizer.apply_chat_template()`.
<!-- /card -->

<!-- card -->
Q: What makes LLMs broadly useful in a way earlier NLP models were not?
A: Generality. One model performs classification, extraction, summarization, translation, and generation with no task-specific training, because all of those tasks can be expressed as text continuation.
<!-- /card -->
