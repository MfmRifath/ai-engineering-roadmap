# A6 — Prompt Engineering

> **Thesis:** A prompt is a set of ingredients you compose deliberately, and the decoding
> parameters are as much a part of the prompt as the words are.

## Why this chapter matters

Alammar's treatment is the *mechanical* one — what the knobs are and what they do to the
distribution. Huyen's ([H5](../../04-ai-engineering-huyen/notes/ch05.md)) is the *engineering* one
— versioning, evaluation, and defense. Read this first for the mechanics; the two complement
rather than repeat each other.

## Core concepts

### Controlling output: the sampling parameters

These operate on the softmax over the vocabulary from
[G4](../../01-hands-on-ml-geron/notes/ch04.md). Knowing what each does to the distribution beats
memorizing recommended values.

| Parameter | Mechanism | Effect |
|---|---|---|
| **temperature** | Divides logits before softmax | <1 sharpens (deterministic); >1 flattens (creative) |
| **top-k** | Keep the *k* highest-probability tokens, renormalize | Hard cap on candidates |
| **top-p** (nucleus) | Keep the smallest set whose cumulative probability ≥ p | **Adaptive** — few candidates when confident, many when not |
| **repetition/frequency penalty** | Downweight already-used tokens | Reduces loops |
| **max_tokens** | Stop after n | Cost and latency control |

**top-p beats top-k** in most cases for exactly the reason in the table: when the model is
confident, top-k=50 still admits 49 bad options; top-p=0.9 admits maybe two. It adapts to the
shape of the distribution.

**`temperature=0` is not truly deterministic** in practice — floating-point non-associativity in
batched GPU kernels, and changing batch composition between requests, produce occasional
variation. Do not build a system that requires bit-identical output.

### The ingredients of a prompt

Alammar's decomposition — treat these as components you decide about individually:

- **Persona** — "You are an experienced technical editor."
- **Instruction** — the actual task.
- **Context** — background the model needs.
- **Format** — the output shape you want.
- **Audience** — who it is for.
- **Tone** — how it should sound.
- **Data** — the input to operate on.

The value is in the checklist. When output is wrong, you can ask *which ingredient is missing*
rather than rewriting blindly.

**Use delimiters** for the data section (`###`, `<data>`, triple quotes). It separates
instructions from content and is your first line of defense against prompt injection
([H5](../../04-ai-engineering-huyen/notes/ch05.md)).

### In-context learning

**Zero-shot** — instructions only. **Few-shot** — include examples.

Examples work well and are underused. What matters:

- **Format consistency** matters more than example count. Inconsistent formatting across examples
  teaches inconsistency.
- **Cover the edge cases**, especially the ones you keep getting wrong.
- **Order affects output** — models exhibit recency bias toward later examples.
- Examples compete for context and cost tokens on every call.

### Chain prompting

Break a complex task into a sequence of prompts, each consuming the last's output. Better
quality, easier debugging (you can see which step failed), each step separately testable — at the
cost of more calls, more latency, and error accumulation.

This is the seed of agent design. [L9](../../05-ai-agents-in-action-lanham/notes/ch09.md) is
chain prompting with tooling around it.

### Reasoning techniques

**Chain-of-thought** — "let's think step by step," or few-shot examples that show reasoning. Works
because the model generates tokens sequentially, each conditioned on the last: intermediate
reasoning tokens become part of the context for the final answer, effectively giving the model
more computation. It cannot do multi-step reasoning "in its head" because there is no head — there
is only the sequence.

`[dated]` Reasoning models (o-series, Claude's extended thinking, DeepSeek-R1) now do this
internally, trained via RL to produce long reasoning traces. For these, explicit CoT prompting is
unnecessary and can even hurt. Know which kind of model you are prompting.

**Self-consistency** — sample the same prompt *n* times at nonzero temperature, take the majority
answer. Better accuracy at *n*× the cost.

> This is **ensembling** ([G7](../../01-hands-on-ml-geron/notes/ch07.md)). Diverse predictors,
> majority vote, errors cancel. Temperature supplies the diversity. Recognizing it as the same
> idea tells you when it will help: when errors are *random*, not systematic. If the model is
> confidently wrong in a consistent way, sampling ten times gets you ten identical wrong answers.

**Tree-of-thought** — explore multiple reasoning branches, evaluate, backtrack. Powerful,
expensive, and rarely worth it outside search-like problems.

### Output verification

Three levels, in increasing strength:

1. **Ask nicely** — "respond with valid JSON." Fails eventually.
2. **Provide examples** — few-shot the exact format. Better.
3. **Constrained/grammar-based sampling** — mask the logits so only tokens valid under a grammar
   can be sampled. **Cannot produce invalid output**, because invalid tokens are unreachable.

Level 3 is the real answer, and it operates at the sampling layer — another demonstration that
decoding is part of prompting. Libraries: Outlines, Guidance, llama.cpp GBNF grammars; most API
providers now offer structured outputs or JSON schema modes.

**Always validate anyway.** Valid JSON is not correct JSON.

## Key code

```python
# The parameters ARE the prompt
out = generator(
    messages,
    temperature=0.0,       # deterministic-ish for extraction/classification
    top_p=1.0,
    max_new_tokens=256,
    repetition_penalty=1.1,
)

# Self-consistency = ensembling over samples
from collections import Counter
answers = [extract_answer(generate(prompt, temperature=0.7)) for _ in range(5)]
final = Counter(answers).most_common(1)[0][0]
```

A prompt assembled from named ingredients, so you can debug it component by component:

```python
PROMPT = """You are {persona}.

{instruction}

Format your answer as {format}.

### Input
{data}
### End input
"""
```

## Gotchas

- **temperature=0 assumed to be reproducible.** Close, not guaranteed. Do not depend on it.
- **Raising temperature to fix a bad answer.** Temperature adds randomness, not competence. If the
  answer is wrong, fix the prompt, the context, or the model.
- **Inconsistent few-shot formatting.** You are teaching inconsistency.
- **Self-consistency on systematic errors.** It corrects random error, not bias. Ten samples of a
  confidently-wrong model give ten wrong answers at ten times the price.
- **Trusting "respond in JSON."** Use constrained decoding, then validate.
- **Data and instructions undelimited.** Injection surface, and the model may confuse the two.
- **Chain-of-thought on a reasoning model.** Can degrade output; those models already do it.
- **Assuming prompt changes are safe.** Prompts are code. Version them, and regression-test them
  ([H5](../../04-ai-engineering-huyen/notes/ch05.md)).

## Exercises

**Understand**
1. What does temperature do to the logits, exactly?
2. Why is top-p usually better than top-k?
3. Why does chain-of-thought improve accuracy, mechanistically?
4. When does self-consistency help, and when does it just cost more?

**Build**
1. Take one prompt and generate at temperatures 0, 0.3, 0.7, 1.0, 1.5. Then hold temperature at
   0.7 and vary top-p over 0.5, 0.9, 1.0. Build the grid and read it.
2. On a reasoning benchmark (GSM8K-style), measure zero-shot vs CoT vs self-consistency with n=5.
   Record accuracy *and* cost. Compute accuracy per dollar.
3. Implement grammar-constrained JSON generation with Outlines or your provider's structured
   output. Then try to make it emit invalid JSON — you should not be able to.
4. Ablate prompt ingredients: start with a full prompt and remove one component at a time.
   Measure which ones actually mattered. Most people never do this and carry cargo-cult prompt
   text for years.

## Flashcards

<!-- card -->
Q: What does temperature do mechanically?
A: Divides the logits by T before the softmax. T < 1 sharpens the distribution toward the argmax; T > 1 flattens it toward uniform. It changes randomness, never competence.
<!-- /card -->

<!-- card -->
Q: Why is top-p usually preferable to top-k?
A: top-k always keeps k candidates regardless of confidence, so when the model is certain it still admits k−1 bad options. top-p keeps the smallest set whose cumulative probability reaches p, adapting to the distribution's shape.
<!-- /card -->

<!-- card -->
Q: Why does chain-of-thought prompting improve accuracy?
A: The model generates tokens sequentially, each conditioned on the previous. Reasoning tokens enter the context and effectively give the model more computation before committing to an answer. It cannot reason "in its head" — there is only the sequence.
<!-- /card -->

<!-- card -->
Q: What classical ML technique is self-consistency, and when does it fail?
A: Ensembling by majority vote, with temperature providing the diversity. It corrects *random* error but not systematic bias — a model that is confidently wrong will produce the same wrong answer n times at n× the cost.
<!-- /card -->

<!-- card -->
Q: What is constrained (grammar-based) decoding and why is it stronger than asking for JSON?
A: It masks the logits at each step so only tokens valid under a grammar can be sampled. Invalid output is unreachable rather than merely discouraged. Asking nicely fails eventually; this cannot.
<!-- /card -->

<!-- card -->
Q: Is `temperature=0` deterministic?
A: Approximately, not guaranteed. Floating-point non-associativity in batched GPU kernels and varying batch composition between requests produce occasional variation. Never build a system requiring bit-identical output.
<!-- /card -->
