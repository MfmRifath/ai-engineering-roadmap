# G12 — Custom Models and Training with TensorFlow

> **Thesis:** Beneath `fit()` there is a loop you can write yourself — and once you have written
> it once, no training code in any framework is opaque again.

## Why this chapter matters

`[dated]` This is the most framework-specific chapter in the book, and you will be writing PyTorch
from Phase 5. **Skim the TF specifics.** But do not skip the two ideas underneath them, because
they transfer completely:

1. **Automatic differentiation** — what a gradient tape actually records, and why.
2. **The custom training loop** — the explicit forward/loss/backward/step cycle that
   [R5](../../03-build-llm-from-scratch-raschka/notes/ch05.md) asks you to write in PyTorch.

Read this chapter as *"here is what `fit()` was doing all along."*

## Core concepts

### Tensors and the immutability rule

`tf.Tensor` is immutable — operations return new tensors. `tf.Variable` is mutable, via
`assign()`. That distinction exists because the autodiff system needs to know what is a parameter
(trainable, tracked) and what is a computation.

TensorFlow is strict about **type coercion**: it will not silently promote float32 to float64, or
int to float. This is deliberate — silent casts hide bugs and cost performance — and it will
annoy you until you appreciate it. PyTorch is more permissive here.

### Customizing the pieces

Nearly everything in Keras can be replaced by a plain function or a subclass:

| Customize | Simple form | Stateful/serializable form |
|---|---|---|
| Loss | a function `(y_true, y_pred)` | subclass `keras.losses.Loss` |
| Metric | a function | subclass `keras.metrics.Metric` |
| Layer | `keras.layers.Lambda` | subclass `keras.layers.Layer` |
| Model | — | subclass `keras.Model` |
| Regularizer / initializer / constraint | a function | subclass the base class |

You subclass instead of using a function when you need **hyperparameters saved with the model**
(implement `get_config`) or **internal state**.

**Metrics vs losses** — a distinction people miss:
- A **loss** must be differentiable (gradients flow through it) and need not be interpretable.
- A **metric** need not be differentiable and *should* be interpretable.

Also, **streaming metrics**: a metric object accumulates across batches (`update_state`,
`result`, `reset_states`). The mean of per-batch accuracies is not the epoch accuracy when
batches differ in size — the streaming version is correct, the naive average is not.

### Automatic differentiation

The core mechanism. A `GradientTape` **records** every operation involving watched tensors during
the forward pass, then replays that graph backwards:

```python
with tf.GradientTape() as tape:
    z = f(w1, w2)
gradients = tape.gradient(z, [w1, w2])
```

Facts worth carrying to any framework:

- A tape is **consumed** by default after one `gradient()` call — use `persistent=True` for more,
  and delete it manually.
- Only `tf.Variable`s are watched automatically. Call `tape.watch(t)` for constants.
- `tf.stop_gradient()` blocks gradient flow through a subgraph — the mechanism behind freezing
  layers, straight-through estimators, and detaching in RL. (PyTorch: `.detach()`.)
- **Numerical stability is not automatic.** Géron's example: `softplus` for large inputs
  overflows in the naive formulation. Frameworks ship stable implementations of `log_softmax`,
  cross-entropy, etc. **Use them rather than composing your own** — this is exactly why you call
  `cross_entropy(logits, targets)` instead of `log(softmax(logits))` in
  [R5](../../03-build-llm-from-scratch-raschka/notes/ch05.md).

### The custom training loop

The thing to internalize. Stripped of TF syntax, it is always:

```
for each epoch:
    for each batch:
        forward pass         -> predictions
        compute loss
        backward pass        -> gradients          # tape.gradient / loss.backward()
        optimizer step       -> update weights     # apply_gradients / optimizer.step()
        reset gradients                            # (PyTorch: zero_grad)
        update metrics
```

Write it when you need something `fit()` cannot express — multiple optimizers for different
parts of the network, unusual gradient manipulation, adversarial training loops. Géron's honest
caveat: **custom loops are longer, more error-prone, and harder to maintain.** Use `fit()` unless
you need not to.

The identical loop appears in PyTorch as:

```python
for xb, yb in loader:
    optimizer.zero_grad()
    loss = criterion(model(xb), yb)
    loss.backward()
    optimizer.step()
```

Recognizing that these are the same four lines is the entire point of the chapter.

### `tf.function` and graph mode

Decorating a Python function with `@tf.function` traces it into a graph, then runs the optimized
graph — pruning unused nodes, fusing operations, running in parallel. Often a large speedup.

The rules that trip everyone up (and which have direct analogues in `torch.compile` and in JAX's
`jit`):

- Only TF operations are traced. Arbitrary Python code runs **once**, at trace time, and its
  effects are baked in. `print()` fires once; `tf.print()` fires every call.
- Python `for` loops over Python data are unrolled at trace time. To keep a loop dynamic, use
  `tf.range` / `tf.while_loop`.
- Calling with a new *shape* or *dtype* triggers **retracing**. Retracing on every call silently
  destroys performance — TF warns about it.
- Side effects (appending to a list, mutating globals) happen only during tracing.

Keras applies `tf.function` automatically inside `fit()`; pass `run_eagerly=True` to disable it
while debugging.

## Key code

```python
# Custom loss with a saved hyperparameter
class HuberLoss(keras.losses.Loss):
    def __init__(self, threshold=1.0, **kwargs):
        self.threshold = threshold
        super().__init__(**kwargs)

    def call(self, y_true, y_pred):
        error = y_true - y_pred
        is_small = tf.abs(error) < self.threshold
        squared = tf.square(error) / 2
        linear = self.threshold * tf.abs(error) - self.threshold**2 / 2
        return tf.where(is_small, squared, linear)

    def get_config(self):                       # required for save/load
        return {**super().get_config(), "threshold": self.threshold}

# The explicit loop
for epoch in range(n_epochs):
    for X_batch, y_batch in batches(X_train, y_train):
        with tf.GradientTape() as tape:
            y_pred = model(X_batch, training=True)   # training=True matters for BN/dropout
            loss = tf.add_n([loss_fn(y_batch, y_pred)] + model.losses)
        grads = tape.gradient(loss, model.trainable_variables)
        optimizer.apply_gradients(zip(grads, model.trainable_variables))
        mean_loss(loss)
    mean_loss.reset_states()
```

## Gotchas

- **Forgetting `training=True` in a custom loop.** Batch norm and dropout behave differently; omit
  it and you silently train in inference mode.
- **Forgetting `model.losses`.** Regularization losses added by layers are *not* included in your
  loss function automatically. `tf.add_n([main_loss] + model.losses)`.
- **Reusing a non-persistent tape.** It is released after one `gradient()` call.
- **Averaging per-batch metrics.** Wrong when batch sizes differ. Use streaming metric objects.
- **Python side effects inside `@tf.function`.** They run at trace time only. Debugging this is
  miserable; use `tf.print`.
- **Silent retracing.** New shapes on every call means graph rebuilds on every call. Watch for
  the warning.
- **Composing your own numerically-unstable ops.** Use the framework's fused `log_softmax` /
  `cross_entropy` rather than `log(softmax(x))`.
- **Missing `get_config`.** Your custom object will not survive save/load.

## Flashcards

<!-- card -->
Q: What is the difference between a loss and a metric?
A: A loss must be differentiable because gradients flow through it, and need not be human-interpretable. A metric need not be differentiable and should be interpretable. Metrics are also *streamed* — accumulated across batches, not averaged per batch.
<!-- /card -->

<!-- card -->
Q: What does a `GradientTape` do?
A: Records every operation involving watched tensors during the forward pass, then replays that graph in reverse to compute gradients. Variables are watched automatically; constants need `tape.watch()`. The tape is released after one `gradient()` call unless `persistent=True`.
<!-- /card -->

<!-- card -->
Q: Write the universal training loop in five steps.
A: Forward pass → compute loss → backward pass for gradients → optimizer step → reset gradients. Identical in TF (`tape.gradient` / `apply_gradients`) and PyTorch (`loss.backward()` / `optimizer.step()` / `zero_grad()`).
<!-- /card -->

<!-- card -->
Q: Why should you use the framework's `cross_entropy` instead of composing `log(softmax(x))`?
A: Numerical stability. The naive composition overflows or underflows for large or small logits; the fused implementation uses the log-sum-exp trick internally.
<!-- /card -->

<!-- card -->
Q: What happens to plain Python code inside a `@tf.function`?
A: It executes only once, at trace time, and its effects are baked into the graph. `print()` fires once; `tf.print()` fires every call. Python loops over Python data are unrolled.
<!-- /card -->

<!-- card -->
Q: What does `tf.stop_gradient` (PyTorch: `.detach()`) do, and where is it used?
A: Blocks gradient flow through part of the graph. Used for freezing layers, straight-through estimators, target networks in RL, and anywhere you want a value without a gradient path.
<!-- /card -->
