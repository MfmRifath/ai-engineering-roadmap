# G2 — End-to-End Machine Learning Project

> **Thesis:** The model is the small part. The project is framing, data, splitting, cleaning,
> feature engineering, validating, and shipping — and every one of those steps has a way of
> silently corrupting your results.

## Why this chapter matters

This is the chapter you will re-read for the rest of your career. It walks the full California
housing project start to finish, and the *sequence* it teaches — frame → get data → explore →
prepare → shortlist → tune → present → deploy → monitor — is the same sequence you will follow
for a RAG system in Phase 7. Only the models change.

Do the whole thing hands-on. Reading it is worth maybe a fifth of doing it.

## Core concepts

### Frame the problem before touching data

Ask, in order:
1. What is the **business objective**? Not "predict house prices" — *how will the prediction be
   used, and by what?* Géron's answer (it feeds a downstream investment system) determines
   everything else.
2. What does the **current solution** look like? That is your baseline, and often it is a
   spreadsheet with 15% error you now have to beat.
3. **Supervised/unsupervised? Regression/classification? Batch/online?** For housing:
   supervised, multiple regression, univariate, batch.
4. What is the **performance measure**, and does it match the objective?

### RMSE vs MAE, and why the choice is about outliers

$$\text{RMSE} = \sqrt{\tfrac{1}{m}\sum (\hat{y}_i - y_i)^2} \qquad \text{MAE} = \tfrac{1}{m}\sum |\hat{y}_i - y_i|$$

RMSE is the ℓ₂ norm, MAE the ℓ₁. The higher the norm index, the more it weights large values —
so **RMSE punishes outliers harder**. Prefer RMSE when errors are roughly bell-shaped; prefer
MAE when you have outliers you do not want to dominate the metric.

This is your first encounter with a theme that runs to the last chapter of Huyen: *the metric
encodes a value judgment.* Choosing RMSE says large errors are disproportionately bad. Say so
out loud.

### Create the test set immediately — and make it stable

Before you look at anything. Human brains overfit: if you explore first, you will pick features
based on patterns you saw in the test data. Géron calls this **data snooping bias**.

Naive `train_test_split` with a fixed seed breaks when the dataset grows — new rows reshuffle
everything and old test rows leak into training. The fix is a **hash of a stable identifier**:

```python
from zlib import crc32
import numpy as np

def in_test_set(identifier, test_ratio):
    # deterministic per row: the same id always lands on the same side,
    # no matter how many rows are added later
    return crc32(np.int64(identifier)) & 0xFFFFFFFF < test_ratio * 2**32
```

### Stratified sampling

Random splits are fine for large datasets, dangerous for small or skewed ones. If median income
strongly predicts price, and your random test set happens to over-represent high earners, your
test score is measuring the wrong population.

Bin the important variable, then sample proportionally within bins:

```python
from sklearn.model_selection import StratifiedShuffleSplit

housing["income_cat"] = pd.cut(housing["median_income"],
                               bins=[0., 1.5, 3.0, 4.5, 6., np.inf],
                               labels=[1, 2, 3, 4, 5])
split = StratifiedShuffleSplit(n_splits=1, test_size=0.2, random_state=42)
```

Géron's comparison table — stratified vs random split error against true proportions — is worth
reproducing yourself. Random sampling is off by several percent; stratified by ~0.01%.

### Explore, then engineer

Correlation first (`housing.corr()`), but remember **Pearson correlation only measures linear
relationships**. Géron's figure of correlation coefficients across various shapes is the thing to
memorize: a perfect parabola has correlation 0.

Then combine attributes. The housing example is the canonical demonstration:

| Feature | Correlation with price |
|---|---|
| `total_rooms` | 0.13 |
| `rooms_per_household` | **0.15** |
| `bedrooms_per_room` | **−0.26** |

`total_rooms` for a district is nearly meaningless — it tracks district size. Divide by
households and it becomes informative. **This is feature engineering, and it beat every model
change in the chapter.**

### Transformation pipelines — the anti-leakage machine

Every transformation must be *fit on training data only* and then applied to validation and test.
Doing this by hand, you will eventually get it wrong. `Pipeline` makes it structural:

```python
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder

num_pipeline = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
    ("attribs_adder", CombinedAttributesAdder()),
    ("std_scaler", StandardScaler()),
])

full_pipeline = ColumnTransformer([
    ("num", num_pipeline, num_attribs),
    ("cat", OneHotEncoder(handle_unknown="ignore"), cat_attribs),
])

X_train = full_pipeline.fit_transform(housing)   # fit + transform
X_test  = full_pipeline.transform(housing_test)  # transform ONLY
```

The imputer's median and the scaler's mean/std are **learned parameters**. Fitting them on the
full dataset leaks test information into training. This is the most common leak in real projects
and it is completely invisible in your metrics.

### Custom transformers

Any class with `fit`, `transform`, and (via `TransformerMixin`) `fit_transform` slots into a
pipeline. Inherit `BaseEstimator` too and you get `get_params`/`set_params`, which is what lets
`GridSearchCV` tune your custom feature engineering as a hyperparameter:

```python
class CombinedAttributesAdder(BaseEstimator, TransformerMixin):
    def __init__(self, add_bedrooms_per_room=True):  # no *args/**kwargs
        self.add_bedrooms_per_room = add_bedrooms_per_room
    def fit(self, X, y=None):
        return self
    def transform(self, X):
        ...
```

### Shortlist, then tune

Train several models quickly and compare with cross-validation before optimizing any of them.
Géron's progression is instructive:

| Model | Train RMSE | CV RMSE | Read |
|---|---|---|---|
| Linear regression | 68,628 | 69,052 | Underfitting |
| Decision tree | **0** | 71,407 | Badly overfitting |
| Random forest | 18,603 | 50,182 | Overfitting, but best so far |

A training RMSE of exactly 0 is not a triumph, it is an alarm.

**`GridSearchCV`** for small, well-understood search spaces; **`RandomizedSearchCV`** when the
space is large — with the same compute, random search explores far more distinct values per
hyperparameter. Both refit the best model on the full training set for you.

### Feature importances, then the single test-set evaluation

`grid_search.best_estimator_.feature_importances_` tells you what to drop. Then, once, you
evaluate on test — and you **do not** go back and tune after seeing that number.

Report a confidence interval, not a point estimate:

```python
from scipy import stats
squared_errors = (final_predictions - y_test) ** 2
stats.t.interval(0.95, len(squared_errors) - 1,
                 loc=squared_errors.mean(),
                 scale=stats.sem(squared_errors))
```

## Gotchas

- **Fitting a scaler or imputer on the full dataset.** The single most common leak. Use pipelines.
- **Exploring before splitting.** Data snooping — you cannot un-see a pattern.
- **`OneHotEncoder` without `handle_unknown="ignore"`.** A category that appears only in
  production crashes the transform. `[dated]` — in modern sklearn this defaults to `"error"`; set
  it explicitly.
- **Scaling the target.** Usually unnecessary for tree models and it complicates inverse-transform
  at prediction time. If you do it, wrap with `TransformedTargetRegressor`.
- **Reading Pearson correlation as "relationship."** It measures *linear* relationship only.
- **Tuning after looking at the test score.** You have now overfit the test set, and you no
  longer have an honest generalization estimate.
- **Forgetting the monitoring plan.** Models decay. Géron insists on it and most projects skip it.

## Flashcards

<!-- card -->
Q: Why fit transformers on the training set only?
A: Transformer parameters (imputation medians, scaler mean/std, encoder categories) are *learned*. Fitting on all data leaks test-set statistics into training, producing optimistic and dishonest validation scores.
<!-- /card -->

<!-- card -->
Q: RMSE vs MAE — when do you pick each?
A: RMSE (ℓ₂) squares errors, so it penalizes large ones disproportionately — use it when errors are roughly Gaussian. MAE (ℓ₁) weights all errors linearly — use it when outliers exist and you don't want them to dominate.
<!-- /card -->

<!-- card -->
Q: What is **data snooping bias**?
A: Exploring the test set (or the full dataset) before splitting, so that your own model and feature choices are shaped by test data. Your brain overfits even when your code doesn't.
<!-- /card -->

<!-- card -->
Q: A decision tree scores RMSE = 0 on training data. What does that tell you?
A: It memorized the training set — severe overfitting. Confirm with cross-validation, where its error will be much worse than a properly regularized model's.
<!-- /card -->

<!-- card -->
Q: `GridSearchCV` or `RandomizedSearchCV`?
A: Grid for small, discrete, well-understood spaces where you want exhaustive coverage. Random for large or continuous spaces — for a fixed compute budget it samples far more distinct values per hyperparameter.
<!-- /card -->

<!-- card -->
Q: Why did `rooms_per_household` beat `total_rooms` as a feature?
A: `total_rooms` for a district mostly encodes district size, not housing quality. Dividing by households turns a size proxy into a meaningful per-unit ratio. Feature engineering outperformed every model change in the chapter.
<!-- /card -->
