# G13 — Loading and Preprocessing Data with TensorFlow

> **Thesis:** Once your model is fast enough, the data pipeline becomes the bottleneck — and the
> fix is always the same: overlap loading with computation so the accelerator never waits.

## Why this chapter matters

Two things survive the TF-specific packaging.

First, the **input pipeline pattern** — shuffle, batch, prefetch, parallelize — is universal.
PyTorch's `DataLoader(num_workers=..., prefetch_factor=..., pin_memory=True)` is the same design.
Raschka's chapter 2 builds a `Dataset` and `DataLoader` for text using exactly this shape.

Second, and more importantly, this is where **embeddings** are introduced as a concrete mechanism
rather than an abstraction. That section is the direct ancestor of everything in
[A2](../../02-hands-on-llms-alammar/notes/ch02.md).

## Core concepts

### The Data API

A `tf.data.Dataset` is a lazy sequence of items with a chainable transformation API. The canonical
pipeline:

```python
dataset = (tf.data.TFRecordDataset(filepaths, num_parallel_reads=4)
           .shuffle(buffer_size=10_000)
           .map(preprocess, num_parallel_calls=tf.data.AUTOTUNE)
           .batch(32)
           .prefetch(1))
```

Each stage matters:

- **`shuffle(buffer_size)`** — fills a buffer and samples from it. **The buffer must be large
  relative to any ordering in your data.** If your file is sorted by label and your buffer holds
  1,000 items, every batch is single-class and training will be a disaster. When the buffer cannot
  be large enough, shuffle the source files themselves too.
- **`map(..., num_parallel_calls)`** — preprocessing on multiple cores.
- **`batch`** — group into batches. `drop_remainder=True` keeps shapes static.
- **`prefetch(1)`** — **the single most important line.** While the GPU trains on batch *n*, the
  CPU prepares batch *n+1*. Without it, CPU and GPU alternate idling and you can halve throughput
  for free.

**Order matters.** `shuffle` then `batch` gives freshly shuffled batches; `batch` then `shuffle`
only shuffles the order of fixed batches — much weaker randomization and a real bug.

`repeat()` before `shuffle` reshuffles each epoch (usually what you want). Also note: the shuffle
buffer's contents are part of the dataset state, so a naive checkpoint/resume does not perfectly
restore the stream.

### TFRecord

TF's binary record format — a sequence of length-prefixed, CRC-checked records, usually holding
serialized `Example` protobufs. The reason it exists: reading millions of small files is
dominated by filesystem overhead. Sharding into a few large sequential files is far faster, and
sharding also enables parallel reads.

`[dated]` Modern equivalents you will actually meet: **Parquet** and **Arrow** for tabular,
**WebDataset** (sharded tars) for large-scale training, and Hugging Face `datasets`, which uses
Arrow with memory-mapping so you can iterate a corpus larger than RAM. The principle — few large
sequential files, read in parallel — is unchanged.

### Preprocessing inside the model

A recurring production bug: training preprocessing and serving preprocessing drift apart, so the
model sees differently-scaled inputs in production than in training. This is **training/serving
skew** and it is nasty precisely because nothing crashes — the numbers just get worse.

The fix is to put preprocessing **inside the model** as layers, so it ships with the weights:

```python
class Standardization(keras.layers.Layer):
    def adapt(self, data_sample):
        self.means_ = np.mean(data_sample, axis=0, keepdims=True)
        self.stds_ = np.std(data_sample, axis=0, keepdims=True)
    def call(self, inputs):
        return (inputs - self.means_) / (self.stds_ + keras.backend.epsilon())
```

The `adapt()` pattern — learn statistics from a sample, then apply them — is exactly
scikit-learn's `fit`/`transform` from [G2](ch02.md), and the same leakage rule applies.

### Categorical features: one-hot vs embedding

The most transferable section in the chapter.

**One-hot encoding** — a vector as wide as the vocabulary, one 1. Fine for small vocabularies.
Catastrophic for large ones: 50,000 categories means a 50,000-dimensional sparse vector per item,
and no notion of similarity between categories. Every pair is equidistant.

**Embedding** — a *dense, trainable* vector per category, typically 10–300 dimensions:

```python
embedding = keras.layers.Embedding(input_dim=vocab_size, output_dim=embedding_dim)
```

Initialized randomly and **learned by gradient descent along with everything else**. Because the
loss pushes categories used in similar contexts toward similar vectors, semantic structure
*emerges* — it is never specified.

Géron's rule of thumb for the dimension: 10 to 300, larger for larger vocabularies and more
complex tasks.

> **This is the single most important paragraph in the chapter.** An `Embedding` layer is a
> lookup table: `embedding(i)` returns row *i* of a `(vocab_size, dim)` matrix. That is *exactly*
> what an LLM's token embedding layer is — GPT-2 small is a (50257, 768) matrix, and
> [R2](../../03-build-llm-from-scratch-raschka/notes/ch02.md) has you build it. When
> [A2](../../02-hands-on-llms-alammar/notes/ch02.md) shows tokens clustering by meaning in
> embedding space, this is the mechanism producing it.

**Out-of-vocabulary handling** uses **oov buckets**: hash unknown categories into a fixed number
of extra slots. Collisions happen; the model learns to live with them. LLM tokenizers avoid the
problem differently — BPE decomposes unknown words into known subwords, so there is no OOV at all
([R2](../../03-build-llm-from-scratch-raschka/notes/ch02.md)).

`[dated]` The `keras.layers` preprocessing family (`Normalization`, `TextVectorization`,
`StringLookup`, `Discretization`) matured after this edition and is now the recommended path.

## Key code

```python
# The pipeline shape that transfers to any framework
ds = (tf.data.Dataset.from_tensor_slices((X, y))
      .shuffle(10_000)          # buffer must be big relative to any ordering
      .map(preprocess, num_parallel_calls=tf.data.AUTOTUNE)
      .batch(32)
      .prefetch(tf.data.AUTOTUNE))   # overlap CPU prep with GPU compute

# The PyTorch equivalent — same four concerns
loader = DataLoader(dataset, batch_size=32, shuffle=True,
                    num_workers=4, prefetch_factor=2, pin_memory=True)

# Embeddings: a trainable lookup table, not a transformation
model = keras.Sequential([
    keras.layers.Embedding(input_dim=50_000, output_dim=128),  # (vocab, dim)
    keras.layers.GlobalAveragePooling1D(),
    keras.layers.Dense(1, activation="sigmoid"),
])
```

## Gotchas

- **A shuffle buffer that is too small.** If data is sorted by class, small buffers produce
  single-class batches and training fails in a way that looks like a model problem.
- **`batch` before `shuffle`.** You shuffle batch order, not example order.
- **Omitting `prefetch`.** Free throughput left on the table; often ~2×.
- **Preprocessing outside the model.** Training/serving skew — silent and slow to diagnose.
- **`adapt()` on the full dataset.** Same leakage rule as [G2](ch02.md): adapt on training data.
- **One-hot encoding a large vocabulary.** Memory explosion and no similarity structure. Embed.
- **Reading millions of small files.** Filesystem overhead dominates. Shard into large files.
- **Assuming perfect checkpoint/resume.** The shuffle buffer's state is part of the stream.

## Flashcards

<!-- card -->
Q: What does `prefetch` do and why does it matter so much?
A: While the GPU trains on batch n, the CPU prepares batch n+1, overlapping the two instead of alternating idle periods. It is frequently a ~2× throughput win for one line of code.
<!-- /card -->

<!-- card -->
Q: Why does the shuffle buffer size matter?
A: `shuffle` samples from a fixed-size buffer, not the whole dataset. If the data has any ordering (e.g. sorted by class) and the buffer is small, batches will be non-representative — often single-class — and training will fail in ways that look like model bugs.
<!-- /card -->

<!-- card -->
Q: One-hot encoding vs embeddings for categorical features?
A: One-hot for small vocabularies: sparse, orthogonal, no similarity structure. Embeddings for large ones: a dense trainable vector per category (typically 10–300 dims), learned by gradient descent, in which semantic similarity emerges rather than being specified.
<!-- /card -->

<!-- card -->
Q: What *is* an `Embedding` layer, mechanically?
A: A trainable lookup table — a (vocab_size, dim) matrix where `embedding(i)` returns row i. An LLM's token embedding layer is exactly this; GPT-2 small's is (50257, 768).
<!-- /card -->

<!-- card -->
Q: What is training/serving skew, and how do you prevent it?
A: Preprocessing at serving time drifts from preprocessing at training time, so the model sees differently-transformed inputs in production. Nothing crashes; quality just degrades. Prevent it by putting preprocessing inside the model as layers, so it ships with the weights.
<!-- /card -->

<!-- card -->
Q: Why shard data into a few large files instead of millions of small ones?
A: Per-file filesystem overhead dominates read time for small files. Large sequential shards read far faster and can be read in parallel across shards. TFRecord, Parquet, and WebDataset all exist for this reason.
<!-- /card -->
